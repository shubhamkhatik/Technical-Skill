## Fundamentals —

| Topic | Core Concepts & Mental Model | Key Techniques | Tradeoffs & Failure Modes | Resources |
| --- | --- | --- | --- | --- |
| **CAP Theorem** | In a distributed system, during a network partition you must choose between **Consistency** (all nodes return the same data) or **Availability** (every request gets a response). Partition tolerance is not optional in real networks — you always have it. The real choice is **CP vs AP** | CP systems (PostgreSQL, HBase, Zookeeper): reject writes during partition to stay consistent. AP systems (Cassandra, DynamoDB, CouchDB): accept writes during partition and sync later (eventual consistency) | ❌ Most engineers misapply CAP. "CA" systems don't exist in distributed deployments — if there's a network, there are partitions. PACELC is a better model: even without partitions, you still trade latency (L) vs consistency (C) | [Jepsen DB Tests](https://jepsen.io/), [PACELC Paper](https://dbmsmusings.blogspot.com/2010/04/problems-with-cap-and-yahoos-little.html) |
| **ACID vs BASE** | **ACID** (Relational DBs): Atomicity (all-or-nothing), Consistency (valid state after tx), Isolation (tx don't interfere), Durability (committed data survives crash). **BASE** (NoSQL): Basically Available, Soft state, Eventually consistent — trades guarantees for scale | ACID: PostgreSQL, MySQL, SQLite — strong guarantees, best for financial/transactional data. BASE: Cassandra, DynamoDB — high write throughput, global distribution, tolerates inconsistency | ❌ "NoSQL scales, SQL doesn't" is a myth. PostgreSQL handles millions of requests with proper indexing and connection pooling. Choose by consistency requirement, not hype | [PostgreSQL ACID](https://www.postgresql.org/docs/current/transaction-iso.html) |
| **Consistency Models** | A spectrum from strong to weak. Stronger = safer but slower. Weaker = faster but complex application logic | **Strong:** every read returns latest write (expensive — requires coordination). **Read-your-writes:** you always see your own updates (session-level). **Monotonic read:** never read older data than you've already seen. **Eventual:** all nodes converge eventually (cheapest) | ❌ Eventual consistency is often misunderstood — it doesn't mean "usually consistent." It means "will be consistent eventually if no new updates." Window of inconsistency can be milliseconds or minutes | [Designing Data-Intensive Applications (Kleppmann) — Ch. 5](https://dataintensive.net/) |
| **Latency vs Throughput** | **Latency** = time for one request. **Throughput** = requests per second. Optimizing one often degrades the other. Batching improves throughput but increases latency. Parallel execution improves latency but reduces throughput efficiency | Measure p50/p95/p99 (percentiles) — not averages. Average hides tail latency. 1% of slow requests still affect 1 in 100 users. Use `autocannon` or `k6` to benchmark | ❌ "Our average latency is 50ms" is misleading — p99 might be 5s. Tail latency causes cascading delays in systems where one request calls 3 services | [Latency Numbers](https://gist.github.com/jboner/2841832) |
| **Scalability — Vertical vs Horizontal** | **Vertical (Scale Up):** bigger machine — more CPU, RAM. Simple, no code changes. Has a hard limit (biggest machine available). **Horizontal (Scale Out):** more machines — requires stateless design, load balancing, distributed state management | Vertical: fastest path to solving a bottleneck. Horizontal: required for true scale but needs: stateless services, shared session store (Redis), distributed cache, sharded DB | ❌ Premature horizontal scaling is a trap — it adds massive complexity before you need it. Optimize and scale vertically first. Most apps never need horizontal scaling | [The 12-Factor App](https://12factor.net/) |
| **Idempotency** | An operation is idempotent if calling it multiple times produces the same result as calling it once. Critical for: safe retries, webhook processing, payment systems | Idempotency key: client sends unique key per operation (`Idempotency-Key: uuid`). Server stores key → result mapping (Redis with TTL). If same key arrives again, return cached result instead of re-executing | ❌ Non-idempotent retries in payment systems = double charges. Non-idempotent webhook handlers = duplicate order creation. Always design mutation endpoints (POST/DELETE) to be idempotent | [Stripe Idempotency](https://stripe.com/docs/idempotency) |
| **Backpressure** | When a consumer processes slower than a producer sends, the buffer fills up → memory exhaustion → crash. Backpressure signals the producer to slow down | Node.js Streams: `writable.write()` returns `false` → pause reading. Queues: bounded queue size → producer blocks when full. Rate limiting: reject excess requests with `429` | ❌ Unbounded queues grow forever under sustained overload — always set `maxLength` on BullMQ queues. In Kafka: consumer lag is the backpressure signal — monitor it | [Backpressure in Node.js](https://nodejs.org/en/learn/modules/backpressure-in-streams) |

## Networking & Traffic Management

| Topic | Core Concepts & Mental Model | Tools & Libraries | Key Techniques | Tradeoffs & Failure Modes | Resources |
| --- | --- | --- | --- | --- | --- |
| **DNS (Domain Name System)** | Translates domain names to IP addresses. Hierarchical: Root → TLD (`.com`) → Authoritative nameserver. DNS responses are cached by TTL — a lower TTL means faster propagation of changes but more DNS lookup load | Route 53 (AWS), Cloudflare DNS, BIND. Record types: `A` (domain→IPv4), `AAAA` (IPv6), `CNAME` (alias), `MX` (email), `TXT` (verification), `NS` (nameserver) | DNS-based load balancing (Weighted routing in Route 53), Geo-DNS (route users to nearest region), failover routing | ❌ Low TTL during migration only — high TTL normally (less DNS queries). DNS changes don't propagate instantly (old TTL must expire first). DNS is UDP-based — can be spoofed (DNSSEC mitigates this) | [Route 53 docs](https://docs.aws.amazon.com/route53) |
| **CDN (Content Delivery Network)** | Globally distributed cache of static assets (JS, CSS, images, video). User requests go to nearest edge node — reduces latency from ~200ms (cross-continent) to ~10ms (edge). Two modes: **Pull CDN** (caches on first request), **Push CDN** (pre-uploaded before request) | Cloudflare *(most popular)*, AWS CloudFront, Fastly, Akamai | Pull CDN: point DNS to CDN, set `Cache-Control` headers. Push CDN: upload assets to CDN origin before deploy. Cache invalidation: versioned filenames (`app.[hash].js`) > TTL-based invalidation | ❌ Stale CDN cache = users seeing old JS/CSS after deploy. Versioned filenames are the only reliable cache-busting strategy. CDN doesn't help for authenticated/dynamic responses — only truly cacheable content | [Cloudflare docs](https://developers.cloudflare.com/) |
| **Load Balancers — L4 vs L7** | **L4 (Transport):** routes by IP + port. Faster, no content inspection. **L7 (Application):** routes by URL, headers, cookies. Enables: path-based routing, SSL termination, sticky sessions, health checks, A/B routing | **Software:** NGINX, HAProxy, Traefik. **Cloud:** AWS ALB (L7) / NLB (L4), GCP Load Balancer. **Algorithms:** Round Robin (default), Least Connections (unequal request durations), Weighted (heterogeneous servers), IP Hash (sticky — avoid for stateless apps) | SSL termination at LB (backend gets plain HTTP), health check endpoint (`/health` → remove unhealthy instance), connection draining (finish in-flight requests before removing instance) | ❌ IP hash "sticky sessions" = unequal load distribution when one IP has many users. Round robin fails when requests have very different durations (use Least Connections instead). No connection draining = dropped requests on deploy | [NGINX Load Balancing](https://docs.nginx.com/nginx/admin-guide/load-balancer/http-load-balancer) |
| **Reverse Proxy** | Sits in front of servers. Client talks to proxy, not directly to servers. Provides: SSL termination, compression, request routing, rate limiting, caching, DDoS protection | NGINX, Caddy, Cloudflare (as global proxy) | `proxy_pass` to upstream, `proxy_set_header X-Real-IP $remote_addr` (preserve client IP), `proxy_cache` (static content caching), gzip at proxy level (faster than at app level) | ❌ Proxy adds one network hop — keep it on the same network as backend (not across regions). NGINX single config error = all traffic down. Test with `nginx -t` before reload | [NGINX docs](https://nginx.org/en/docs) |
| **API Gateway** | Entry point for all client requests in a microservices architecture. Provides: authentication, rate limiting, request routing, protocol translation, response aggregation, logging | AWS API Gateway, Kong, Traefik, NGINX, Envoy | Auth at gateway (not every service), rate limit per route, route `/api/users` → Users Service, `/api/orders` → Orders Service, request/response transformation, API versioning | ❌ API Gateway is a single point of failure — deploy in HA (multiple instances + LB). Gateway doing too much (business logic) = bottleneck. Too many hops (client → gateway → service A → service B) = latency accumulation | [Kong docs](https://docs.konghq.com/) |

## Database Architecture at Scale

| Topic | Core Concepts & Mental Model | Tools & Libraries | Key Techniques | Tradeoffs & Failure Modes | Resources |
| --- | --- | --- | --- | --- | --- |
| **Replication** | Copy data across multiple nodes. **Primary-Replica (Master-Slave):** all writes go to primary, reads can go to any replica. **Multi-Primary:** any node accepts writes (conflict resolution needed). **Synchronous:** primary waits for replica ACK before confirming write (no data loss, higher latency). **Asynchronous:** primary confirms without waiting (lower latency, possible data loss on crash) | PostgreSQL streaming replication, MySQL replication, MongoDB replica sets, AWS RDS Multi-AZ | Read replicas for read-heavy workloads, failover to replica on primary crash, replica lag monitoring (`pg_stat_replication`) | ❌ Replica lag: writes to primary, immediate read from replica = stale data (use "read-your-writes" consistency, read from primary for critical reads). Async replication data loss window on crash | [PostgreSQL Replication](https://www.postgresql.org/docs/current/high-availability.html) |
| **Sharding (Horizontal Partitioning)** | Split a large table across multiple database instances. Each shard holds a subset of data. **Hash sharding:** `shard = hash(userId) % numShards` — even distribution. **Range sharding:** `shard = userId range` — supports range queries but hot spots. **Directory sharding:** lookup table maps key to shard | MongoDB (native sharding), Vitess (MySQL sharding), PostgreSQL + Citus, AWS DynamoDB (partitioned by key) | Shard key design (most important decision — wrong key = hot shard), cross-shard queries (avoid — expensive), resharding strategy when adding shards | ❌ Hot shards: all traffic goes to one shard (e.g., sharding by `createdAt`  • high insert rate = newest shard is hot). Cross-shard JOINs are expensive — denormalize or use application-level joins. Resharding (redistribution) is operationally painful | [Designing Data-Intensive Applications — Ch. 6](https://dataintensive.net/) |
| **Indexing at Scale** | Without indexes = full table scan on every query. B-tree index handles: equality and range queries. Hash index: equality only, faster. Composite index: column order matters (most selective first). Covering index: query satisfied entirely by index (no table access) | PostgreSQL `EXPLAIN ANALYZE`, `CREATE INDEX CONCURRENTLY` (non-blocking), partial indexes (`WHERE deleted_at IS NULL`), GIN for arrays/JSON/full-text | Run `EXPLAIN ANALYZE` before and after index. Use `pg_stat_user_indexes` to find unused indexes. `CREATE INDEX CONCURRENTLY` in production (avoids table lock) | ❌ Too many indexes = slow writes (every write updates all indexes). Index on low-cardinality column (e.g., `boolean`) is wasteful. Composite index `(a, b)` helps `WHERE a = ?` but NOT `WHERE b = ?` alone | [Use the Index, Luke](https://use-the-index-luke.com/) |
| **Connection Pooling** | Each DB connection is expensive (~1-10MB RAM, TCP overhead). Without pooling, a Node.js app with 100 concurrent requests = 100 DB connections → PostgreSQL collapses (default max 100-200 connections) | **PgBouncer** (connection pooler for PostgreSQL), Prisma built-in pool (`connection_limit`), `pg` pool (`new Pool({ max: 10 })`), RDS Proxy (AWS managed) | Pool size = `(num_cores * 2) + disk_spindles` (PgBouncer formula). Session vs transaction vs statement pooling modes. Monitor pool wait queue | ❌ Pool too small = requests queue up waiting for a connection. Pool too large = DB overwhelmed. PgBouncer transaction mode incompatible with prepared statements — use session mode or disable prepared statements | [PgBouncer docs](https://www.pgbouncer.org/) |
| **Database Selection Guide** | Choose by data model + consistency requirement + scale need — not popularity | **PostgreSQL:** relational, ACID, complex queries, default choice. **MongoDB:** document, flexible schema, rapid iteration. **Cassandra/DynamoDB:** wide-column, AP, high write throughput, time-series. **Redis:** key-value, in-memory, caching/sessions. **Neo4j:** graph, relationship queries. **ClickHouse:** OLAP, analytics, columnar. **Elasticsearch:** full-text search, log analysis | Start with PostgreSQL. Add Redis for caching. Add Elasticsearch for search. Only add Cassandra/Dynamo when you have genuine write-scale problems | ❌ Using MongoDB because "it's flexible" = inconsistent schema at scale. Using Cassandra because "it's fast" without understanding eventual consistency model = data bugs | [Choosing a Database - Martin Fowler](https://martinfowler.com/articles/nosql-distilled.html) |

## Caching Architecture

| Topic | Core Concepts & Mental Model | Tools & Libraries | Key Techniques | Tradeoffs & Failure Modes | Resources |
| --- | --- | --- | --- | --- | --- |
| **Caching Layers** | Cache exists at multiple levels — each has different scope, speed, and invalidation complexity | **Browser:** `Cache-Control` headers, service worker. **CDN:** Cloudflare, CloudFront — static assets + cacheable API responses. **Server (in-memory):** `node-cache`, `lru-cache` — single instance only. **Distributed:** Redis — shared across all instances. **DB query cache:** PostgreSQL shared buffers | Layer order: Browser → CDN → Server memory → Redis → Database. Cache hit at any layer = don't proceed to next | ❌ Server in-memory cache in clustered apps = each instance has its own cache (inconsistent). Redis becomes a single point of failure — use Redis Sentinel or Cluster | [Redis caching patterns](https://redis.io/docs/manual/patterns) |
| **Cache-Aside (Lazy Loading)** | Application manages the cache explicitly. Read: check cache → miss → read DB → write to cache → return. Write: update DB → **invalidate** cache key (don't update cache — it might be stale). Most common pattern | Redis + your DB | Cache key design (`users:${id}`, `posts:${userId}:page:${page}`), TTL per data type (user profile: long TTL, real-time feed: short TTL), cache warming on startup for hot data | ❌ Cache miss penalty on first request (thundering herd if cache expires under high load — add jitter to TTLs). Stale cache if DB updates without invalidating cache key. Data consistency lag between DB and cache | — |
| **Write-Through** | Write to cache AND DB simultaneously on every write. Cache is always in sync with DB. Read is always a cache hit (after first write). More expensive writes | Redis + ORM transaction-like wrapper | Write to both in same operation, cache miss on first read (before any write), good for write-heavy + read-heavy workloads where consistency matters | ❌ Every write hits both cache and DB — higher write latency. Cache stores data that may never be read (wasted memory). If DB write fails after cache write = inconsistency | — |
| **Write-Back (Write-Behind)** | Write to cache only, immediately return. Persist to DB asynchronously in the background. Fastest writes possible | Redis + background worker (BullMQ) | Batch DB writes for efficiency, reduce DB write load, use for metrics/counters/analytics where occasional data loss is acceptable | ❌ Data loss risk: if cache crashes before DB write = lost data. Complex to implement correctly. Not suitable for critical transactional data | — |
| **Cache Invalidation** | The hardest problem in distributed systems. When data changes in DB, cache must be invalidated. Three strategies: **TTL** (automatic expiry), **Event-based** (invalidate on write), **Version keys** (`users:${id}:v${version}`) | `redis.del(key)` on write, `revalidateTag()` in Next.js, event-driven invalidation via message queue | Tag-based invalidation (invalidate all keys with tag `user:123`), cache stampede protection (mutex/lock on cache miss), short TTL + stale-while-revalidate | ❌ Phil Karlton: "There are only two hard things in Computer Science: cache invalidation and naming things." Missing an invalidation = stale data visible to users. Mass invalidation under load = thundering herd hits DB | — |

## Async Processing & Messaging

| Topic | Core Concepts & Mental Model | Tools & Libraries | Key Techniques | Tradeoffs & Failure Modes | Resources |
| --- | --- | --- | --- | --- | --- |
| **Message Queues** | Decouple producer (writes job) from consumer (processes job). Producer returns immediately — consumer processes async. Buffer against traffic spikes — queue absorbs burst, consumer processes at its pace | **BullMQ + Redis** *(Node.js standard, job queues)*, **AWS SQS** *(managed, simple)*, **RabbitMQ** *(flexible routing)*. Queue vs Topic: queue = one consumer per message. Topic/pub-sub = multiple consumers per message | Job priorities, delayed jobs, retries with exponential backoff, dead-letter queue (DLQ) for failed jobs, job deduplication, worker concurrency tuning | ❌ No DLQ = failed jobs silently disappear. No idempotency in consumer = duplicate processing on retry causes double-sends/double-charges. Unbounded queue = memory exhaustion under sustained overload. BullMQ requires Redis — plan for Redis HA | [BullMQ docs](https://docs.bullmq.io/) |
| **Event Streaming (Kafka)** | Persistent, ordered, replayable event log. Unlike queues (message deleted after consumption), Kafka retains messages for configured retention period. Consumers track their own offset (position in log) — can replay from any point | Apache Kafka, AWS MSK (managed Kafka), Confluent Cloud, Redpanda (Kafka-compatible, faster) | Topics + Partitions (parallelism unit), Consumer Groups (each group gets all messages independently), offset management (`auto.commit` vs manual), Kafka Streams for real-time processing, Schema Registry for event schema evolution | ❌ Partition count is set at creation — changing requires migration. Message ordering guaranteed only within a partition. Kafka is operationally complex — use Confluent or MSK in production. Wrong partition key = all messages in one partition = no parallelism | [Kafka docs](https://kafka.apache.org/documentation) |
| **Event-Driven Architecture** | Services communicate via events (something that happened) instead of commands (do this). Loose coupling — publisher doesn't know consumers. Enables: audit log, event replay, multiple independent consumers | Kafka, AWS EventBridge, RabbitMQ (topic exchange), Redis pub/sub (simple, no persistence) | Event schema design: `{ eventType, version, timestamp, payload }`. Event versioning (backward-compatible changes only). Choreography (services react to events independently) vs Orchestration (central coordinator directs services) | ❌ Eventually consistent by nature — services see events at different times. Event schema changes break consumers (use schema registry + versioning). Choreography = hard to trace end-to-end flow (use distributed tracing). Orchestration = central coordinator is a coupling point | [Martin Fowler — Event-Driven](https://martinfowler.com/articles/201701-event-driven.html) |
| **Saga Pattern** | Manage distributed transactions across multiple services without a global ACID transaction (which doesn't exist across services). Sequence of local transactions with compensating actions if something fails | Orchestration-based (Temporal, AWS Step Functions) or Choreography-based (Kafka events) | Example: Order saga — `Reserve Inventory → Charge Payment → Notify Shipping`. If payment fails → `Release Inventory` (compensating action). Each step is idempotent | ❌ Sagas are eventually consistent — intermediate states are visible. Compensating transactions are hard to design correctly (not always reversible — e.g., "send email" can't be unsent). Choreography-based sagas are hard to debug (events scattered across services) | [Saga Pattern](https://microservices.io/patterns/data/saga.html) |

## Reliability & Fault Tolerance

| Topic | Core Concepts & Mental Model | Tools & Libraries | Key Techniques | Tradeoffs & Failure Modes | Resources |
| --- | --- | --- | --- | --- | --- |
| **Circuit Breaker** | Prevent cascading failures. If Service A calls Service B and B is slow/failing, A's threads pile up waiting → A also fails → everything cascades. Circuit breaker tracks failure rate — when threshold exceeded, "opens" the circuit (fail fast without calling B) | Three states: **Closed** (normal, calls pass through), **Open** (failing fast, not calling B), **Half-Open** (probe — try one request to see if B recovered). `opossum` (Node.js), Resilience4j (Java), AWS App Mesh | Failure threshold (e.g., 50% errors in 10s = open), recovery timeout (e.g., 30s half-open), fallback response (cached data, default value, graceful degradation message) | ❌ Circuit breaker on every call = too many half-open probes = can't distinguish load spike from actual failure. Too sensitive (low threshold) = opens on transient errors. Too insensitive (high threshold) = doesn't prevent cascade | [opossum (Node.js)](https://nodeshift.dev/opossum) |
| **Retry with Exponential Backoff + Jitter** | Transient failures (network glitch, rate limit, timeout) are recoverable. Retry with increasing delays. Without jitter, all clients retry simultaneously → thundering herd on recovering service | `axios-retry`, `p-retry`, custom: `delay = Math.min(base * 2^attempt + random(0, 100ms), maxDelay)` | Retry only idempotent operations (GET, PUT — not POST unless idempotent). `Retry-After` header from server. Max retry count (3-5). Don't retry on 4xx (client error) — only 5xx / network errors | ❌ Retrying non-idempotent POST = double order. No jitter = synchronized retry storm. Infinite retries = memory/connection exhaustion. Retry budget: if >X% of requests are retries, stop retrying | — |
| **Bulkhead Pattern** | Isolate failures to one part of the system. Named after ship bulkheads — if one compartment floods, others stay dry. Use separate thread pools / connection pools per downstream service so one slow service can't exhaust all resources | Separate DB connection pools per service, separate HTTP clients per third-party API, separate queue workers per job type, Kubernetes resource limits per pod | Connection pool per external service: `{ authService: pool(max:5), paymentService: pool(max:3), emailService: pool(max:2) }`. If payment service is slow, it only exhausts its 3 connections — auth service still works | ❌ Too many small pools = under-utilization of total capacity. Hard to set pool sizes without profiling. Adds configuration overhead — apply to critical isolation points, not everywhere | — |
| **Rate Limiting Algorithms** | Four approaches with different tradeoffs. **Fixed Window:** count per time window — simple but burst at boundary. **Sliding Window Log:** precise but memory-heavy. **Sliding Window Counter:** good balance. **Token Bucket:** allows controlled bursts above average rate | Redis-based: `rate-limit-redis`, `@upstash/ratelimit`. Algorithms: Upstash has all four. Per-IP for public, per-userId for authenticated, per-API-key for B2B | `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` headers, `429 Too Many Requests`  • `Retry-After` header, distributed rate limiter (Redis) for multi-instance apps | ❌ Fixed window: burst attack — 1000 requests in last second of window + 1000 in first second of next = 2000 requests in 2 seconds. Token bucket: hard to tune burst size correctly. Per-IP limiting: IPv6 users can rotate IPs | [Cloudflare Rate Limiting](https://developers.cloudflare.com/waf/rate-limiting-rules) |
| **Health Checks — Liveness vs Readiness** | **Liveness:** is the process alive and not deadlocked? Fail → restart container. **Readiness:** is the service ready to receive traffic? Fail → remove from load balancer rotation (don't restart). These are different checks for different purposes | Kubernetes: `livenessProbe`  • `readinessProbe`. AWS ALB target group health checks. Express: `GET /health/live` and `GET /health/ready` | Liveness: simple `{ status: 'alive' }` — just confirms process is running. Readiness: check DB connection, Redis, critical dependencies. Return `503` if not ready | ❌ Liveness check that tests DB = one DB hiccup restarts all your pods simultaneously. Readiness check with `SELECT 1` = DB query on every probe (add caching). Startup probe (Kubernetes) for slow-starting apps — prevents premature liveness failures | — |

## Microservices Architecture

| Topic | Core Concepts & Mental Model | Tools & Libraries | Key Techniques | Tradeoffs & Failure Modes | Resources |
| --- | --- | --- | --- | --- | --- |
| **Microservices vs Monolith** | **Monolith:** single deployable unit — simple to develop, test, debug, deploy. **Microservices:** independent services per business domain — independent deploy, scale, and failure isolation. **Rule:** start with a monolith. Extract to services when you have team scaling, independent scaling, or independent deployment needs — not before | Monolith: Express/NestJS/Next.js. Microservices: Docker + Kubernetes + API Gateway + service mesh | Modular monolith first (feature-based folder structure, clear boundaries), extract service when: team > 2 pizza rule per module, service has wildly different scaling needs, or independent deploy is required | ❌ "Microservices from day one" = distributed monolith (services too coupled) + all the operational overhead of microservices + none of the benefits. Each service needs its own CI/CD, monitoring, and oncall — multiply operational cost by number of services | [Martin Fowler — Microservices](https://martinfowler.com/articles/microservices.html) |
| **Service Discovery** | In dynamic environments (Kubernetes, auto-scaling), service IPs change constantly. Service discovery lets services find each other without hardcoded IPs | **Client-side:** service queries registry (`Consul`, `Eureka`) and load-balances itself. **Server-side:** load balancer queries registry (more common in Kubernetes). **DNS-based (Kubernetes):** `http://users-service.default.svc.cluster.local` — built-in | Kubernetes DNS resolves service names automatically (no external registry needed). Health-check integration removes unhealthy instances from registry | ❌ Stale registry entries if service deregisters poorly. Client-side discovery = every service needs a smart client library. Kubernetes DNS is the simplest — use it unless you have cross-cluster needs | [Kubernetes Service Discovery](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service) |
| **Service Mesh** | Infrastructure layer that handles all service-to-service communication: mTLS (encrypted service comm), load balancing, circuit breaking, retries, distributed tracing — without touching application code | Istio *(powerful, complex)*, Linkerd *(lightweight, simpler)*, Consul Connect | Sidecar proxy pattern (Envoy proxy injected alongside each pod), mTLS between all services (zero-trust networking), traffic policies without code changes | ❌ Service mesh adds latency (sidecar proxy hop on every service call). Istio is operationally complex — significant learning curve. Overkill for small microservice setups (< 10 services) — use explicit HTTP auth + circuit breaker libraries instead | [Istio docs](https://istio.io/docs) |
| **12-Factor App** | Methodology for building stateless, scalable, deployable services. Core principles that enable horizontal scaling | 1. Config in env vars (not code). 2. Stateless processes (no in-memory state). 3. Port binding (self-contained). 4. Dev/prod parity (same stack everywhere). 5. Disposability (fast startup, graceful shutdown). 6. Logs as streams (stdout, not files) | Each principle enables a specific operational capability. Stateless processes = horizontal scaling. Config in env = environment promotion without code changes. Logs as streams = works with any log aggregator | ❌ Strict 12-factor with legacy systems = big refactor. Some state is necessary (use Redis for it). Don't apply dogmatically — understand the principle behind each factor | [12factor.net](http://12factor.net) |

## Observability — Logs, Metrics, Traces

> **Mental Model:** Observability is asking "what is my system doing right now and why?" Monitoring tells you *that* something is wrong. Observability tells you *why*. Three pillars: **Logs** (what happened), **Metrics** (how much / how fast), **Traces** (which path a request took through your system).
> 

| Topic | Core Concepts & Mental Model | Tools & Libraries | Key Techniques | Tradeoffs & Failure Modes | Resources |
| --- | --- | --- | --- | --- | --- |
| **Structured Logging** | Logs must be JSON in production. Structured logs are queryable, filterable, and machine-parseable. `console.log()` is unstructured noise | **Pino** *(fastest Node.js JSON logger)*, Winston, Bunyan. Log aggregators: **Datadog**, **Loki + Grafana** *(open source)*, ELK Stack (Elasticsearch + Logstash + Kibana), AWS CloudWatch | Log levels (`trace`/`debug`/`info`/`warn`/`error`/`fatal`), structured fields (`{ requestId, userId, duration, statusCode }`), correlation ID per request (trace across service calls), redact sensitive fields | ❌ Logging PII (passwords, tokens, card numbers) = compliance violation. Too verbose in prod = storage cost + noise. `console.log` in prod = unqueryable. Logging synchronously in hot path = I/O blocks event loop (Pino is async by default) | [Pino docs](https://getpino.io/) |
| **Metrics** | Quantitative measurements over time. Four types: **Counter** (cumulative, only goes up — requests total, errors total), **Gauge** (current value — memory usage, queue depth), **Histogram** (distribution — request duration p50/p95/p99), **Summary** (like histogram, client-side) | **Prometheus** (scrape-based, stores time-series), **Grafana** (dashboards), **Datadog** (managed), **StatsD**, `prom-client` (Node.js Prometheus client) | Expose `/metrics` endpoint for Prometheus scraping. Alert on: error rate > 1%, p99 latency > 1s, queue depth > 1000, disk usage > 80%. Use RED method: Rate, Errors, Duration | ❌ Average latency metric is misleading — use histograms (p50/p95/p99). Too many metric labels (high cardinality) = Prometheus performance issues. Alert on symptoms (slow response) not causes (high CPU) | [Prometheus docs](https://prometheus.io/docs), [Grafana docs](https://grafana.com/docs) |
| **Distributed Tracing** | Track a single request across multiple services. Each service adds a span to the trace. Visualize the full request path, identify which service is slow, where errors originate | **OpenTelemetry** *(standard SDK, vendor-neutral)*, **Jaeger** *(open source)*, **Zipkin**, **Datadog APM**, **AWS X-Ray** | Trace ID propagated in HTTP headers (`traceparent`), spans represent individual operations (DB query, HTTP call, queue publish), parent-child span relationships, sample rate (don't trace 100% in prod — 1-10% is enough) | ❌ Tracing everything at 100% = significant overhead. Missing header propagation at one service = broken trace chain. OpenTelemetry auto-instrumentation doesn't capture business context — add custom spans for important operations | [OpenTelemetry Node.js](https://opentelemetry.io/docs/instrumentation/js) |
| **Alerting Strategy** | Alert on user-impacting symptoms first. Too many alerts = alert fatigue = alerts ignored. Too few = silent outages | PagerDuty, Opsgenie, Grafana alerts, Datadog monitors | Alert on: error rate, p99 latency, availability. NOT on: CPU usage, memory (symptom, not impact). Runbook links in every alert. On-call rotation. Severity levels (P1 = wake someone up, P3 = fix next business day) | ❌ Alerting on CPU > 80% = noisy and unactionable. Single threshold alerts miss gradual degradation — use anomaly detection. No runbook = oncall engineer guesses what to do at 3am | [Google SRE Book](https://sre.google/sre-book/monitoring-distributed-systems) |

## AI System Design

> **Mental Model:** AI backends have unique characteristics: **high latency** (1-30s per LLM call), **non-deterministic outputs**, **high cost per request**, **token-based pricing**, and **stateful conversations**. Standard backend patterns still apply — but you need additional patterns for prompt management, semantic caching, streaming, and evaluation.
> 

| Topic | Core Concepts & Mental Model | Tools & Libraries | Key Techniques | Tradeoffs & Failure Modes | Resources |
| --- | --- | --- | --- | --- | --- |
| **LLM API Integration** | LLMs are external HTTP APIs. The backend's job: validate input, call API, handle streaming, manage errors, track costs, and never expose API keys to the client | OpenAI SDK, Anthropic SDK, Google Gemini SDK, Vercel AI SDK (unified interface). Models: `gpt-4o`, `claude-sonnet-4-5`, `gemini-1.5-pro` | Always call from backend (API key security), streaming via SSE (`res.write(chunk)`), timeout handling (`AbortController` — LLM calls can take 30s+), token counting before call to stay within limits, track `usage.total_tokens` per call for cost monitoring | ❌ Calling LLM from frontend = API key exposed in network tab. No timeout = hanging request hangs the server. No streaming = user waits 10-30s for blank screen then full response (terrible UX). No error handling for `429` (rate limit) / `503` (overload) | [OpenAI Node SDK](https://github.com/openai/openai-node), [Anthropic SDK](https://github.com/anthropic/sdk-python) |
| **Streaming LLM Responses** | LLMs generate tokens one by one. Streaming sends each token to the client as it's generated. User sees text appear progressively (ChatGPT-style) — dramatically better perceived performance | Server-Sent Events (SSE): `text/event-stream`, `ReadableStream` (Web Streams API), Vercel AI SDK `streamText`, OpenAI `.stream()` method | `data: {"token": "Hello"}\n\n` SSE format, `[DONE]` signal on completion, handle client disconnect (abort upstream LLM call to save cost), reconnect with `Last-Event-ID` for resumable streams | ❌ No client disconnect handling = LLM keeps generating after user navigates away (wasted tokens = wasted money). Buffering the full response before sending = no streaming benefit. SSE proxy chain must not buffer (NGINX: `proxy_buffering off`) | [Vercel AI SDK](https://sdk.vercel.ai/) |
| **RAG — Retrieval-Augmented Generation** | LLMs have a knowledge cutoff and limited context window. RAG extends LLM knowledge by retrieving relevant documents at query time and injecting them into the prompt. The system "retrieves" then "generates" | Pipeline: `User Query → Embed Query → Vector Search → Retrieve Chunks → Build Prompt → LLM → Response`. Tools: **LangChain.js** / **LlamaIndex.TS** (orchestration), **pgvector** / **Pinecone** / **Weaviate** (vector store), OpenAI Embeddings / `text-embedding-3-small` | Chunking strategy (fixed-size vs semantic — overlapping chunks reduce context loss at boundaries), embedding model consistency (same model for indexing and querying), top-k retrieval (k=3-5 chunks), re-ranking (re-order chunks by relevance after initial retrieval), metadata filtering (filter by date, category before vector search) | ❌ Wrong chunk size: too small = no context, too large = exceeds context window. Embedding model change invalidates all stored vectors (must re-index). Retrieving irrelevant chunks = LLM hallucinates from bad context ("garbage in, garbage out"). No source citation = unverifiable answers | [LangChain.js](https://js.langchain.com/), [LlamaIndex.TS](https://ts.llamaindex.ai/) |
| **Semantic Caching** | LLM calls are expensive (cost) and slow (latency). Semantically similar questions should return cached answers — not just identical strings. "What's the weather?" and "How's the weather today?" are semantically equivalent | Redis + vector similarity: embed the query, search cache for similar embeddings, if similarity > threshold (e.g., 0.95 cosine similarity), return cached response. Tools: `GPTCache`, custom Redis + pgvector | Cache key = query embedding (not the query string). TTL based on data volatility (FAQ answers: long TTL, real-time data: no cache). Cache hit threshold tuning (too low = wrong cached answers, too high = rarely hits) | ❌ Threshold too low = semantically different questions get same cached answer. No TTL = outdated cached responses. Caching personalized responses without user ID in cache key = data leak between users | [GPTCache](https://github.com/zilliztech/GPTCache) |
| **Prompt Engineering & Management** | Prompts are the API contract with the LLM. They need versioning, testing, and management like code. A 20-word change in a system prompt can change model behavior significantly | **LangSmith** (prompt tracking + eval), **Langfuse** *(open-source)*, **Promptfoo** (prompt testing), plain Git for simple cases | System prompt vs user message separation, few-shot examples for consistent output format, output format instruction (`Respond ONLY in JSON. Do not include markdown`), prompt versioning (`prompts/v1/qa.txt`), A/B test prompt variants | ❌ Hardcoded prompts in source code = no visibility into prompt performance. No output format enforcement = unparseable LLM responses break your app. Prompt injection: user message overrides system prompt (`Ignore previous instructions and...`) — sanitize user input, use structured inputs | [Langfuse docs](https://langfuse.com/docs) |
| **LLM Evaluations (Evals)** | LLMs are non-deterministic — you can't assert `output === expected`. Evals measure quality across dimensions: correctness, relevance, groundedness, toxicity. Required before deploying prompt or model changes | **Promptfoo** (open-source eval framework), **LangSmith**, **Ragas** (RAG-specific: context precision, context recall, answer faithfulness), **DeepEval** | LLM-as-judge (use GPT-4 to grade your GPT-3.5 outputs), human evaluation for critical paths, regression suite (run after every prompt change), dataset of representative inputs + expected outputs | ❌ No evals = blind deployment. LLM-as-judge has its own biases (self-preference, length bias). Evals on too small a dataset = false confidence. RAG-specific: answer can be factually correct but not grounded in retrieved context (hallucination) | [Ragas docs](https://docs.ragas.io/), [Promptfoo docs](https://promptfoo.dev/) |
| **Token & Cost Management** | LLM pricing is per token. GPT-4o: ~$5/1M input tokens. At scale, costs compound rapidly. Must track, budget, and optimize token usage | `tiktoken` (OpenAI tokenizer — count tokens before calling API), `anthropic.messages.countTokens()`, LangSmith / Langfuse (cost tracking per call) | Truncate conversation history to fit context window (sliding window — keep last N messages), use cheaper model for simple tasks (`gpt-4o-mini` for classification, `gpt-4o` for complex reasoning), cache embeddings (don't re-embed unchanged documents), batch embedding API calls | ❌ Unbounded conversation history = context window exceeded + expensive. No model routing = using GPT-4o for tasks that GPT-4o-mini handles fine (10x cost difference). Logging full prompts + completions = significant storage cost at scale | — |
| **AI Agent Architecture** | Agents use LLMs to reason over multiple steps, call tools (functions), and take actions. The LLM decides which tool to call, calls it, observes the result, and continues until the task is done | **LangGraph** (stateful agent graphs), **LangChain agents**, **OpenAI Assistants API**, **Vercel AI SDK** `generateText` with tools | Tool definition (name + description + parameters Zod schema), tool execution + result injection, agent loop (ReAct pattern: Reason → Act → Observe), max iterations to prevent infinite loops, human-in-the-loop for dangerous tools | ❌ Agents can loop forever without max iteration limit. LLM hallucinating tool parameters = tool call with invalid inputs (validate tool inputs with Zod). Agents are slow (multiple LLM calls + tool executions) — not suitable for low-latency use cases. Insufficient tool descriptions = LLM picks wrong tool | [LangGraph docs](https://langchain-ai.github.io/langgraphjs) |
| **AI System Design Considerations** | Unique architectural concerns that differ from standard backend design | Rate limiting: LLM API has its own rate limits (requests/min, tokens/min) — implement queue + retry with backoff. Fallback: primary model unavailable → fallback to cheaper/different model. Multi-tenancy: per-tenant token budgets and rate limits. Async for long tasks: don't wait 30s in HTTP handler — queue LLM jobs, return job ID, client polls or receives webhook | — | ❌ No fallback model = LLM provider outage = your whole product down. No per-tenant rate limiting = one heavy user exhausts your API quota for all users. Synchronous LLM call in webhook handler that must respond in 3s = timeout | [Anthropic API docs](https://docs.anthropic.com/) |

## Cloud Architecture Patterns

| Topic | Core Concepts & Mental Model | Tools & Libraries | Key Techniques | Tradeoffs & Failure Modes | Resources |
| --- | --- | --- | --- | --- | --- |
| **Strangler Fig Pattern** | Incrementally replace a legacy monolith with new services — module by module. New requests go to the new service; old requests still go to the monolith. Gradually move all traffic to new services, then decommission the monolith | NGINX / API Gateway for traffic routing, feature flags for gradual cutover | Route by URL path or feature flag, run both systems in parallel during migration, shared DB (temporarily — until data ownership is clear), anti-corruption layer between legacy and new | ❌ "Big bang" rewrite fails 90% of the time — the strangler fig pattern is how successful migrations happen. Shared DB during migration = coupling that's hard to remove. Skipping the anti-corruption layer = legacy data model pollutes new services | [Martin Fowler — Strangler Fig](https://martinfowler.com/bliki/StranglerFigApplication.html) |
| **CQRS (Command Query Responsibility Segregation)** | Separate the read model from the write model. Writes (Commands) go to a normalized write DB. Reads (Queries) go to a denormalized read DB optimized for specific queries. Updates propagate from write DB to read DB via events | Kafka (sync between write and read model), separate PostgreSQL for writes + Elasticsearch for reads, MongoDB for complex read queries | Write side: ACID, normalized, optimized for consistency. Read side: denormalized, pre-aggregated, optimized for query patterns. Event sourcing: store events as the source of truth (derive state by replaying events) | ❌ CQRS adds significant complexity — only adopt when read and write scale requirements genuinely differ. Read model is eventually consistent — visible delay between write and read. Event sourcing makes simple queries require replaying events | [Martin Fowler — CQRS](https://martinfowler.com/bliki/CQRS.html) |
| **Anti-Corruption Layer** | When integrating with a legacy system or third-party API with a different data model, the ACL translates between the two models. Prevents legacy concepts from leaking into your clean domain model | Adapter/Translator pattern, custom mapping layer | Define your own domain model independently, translate at the boundary (incoming + outgoing), never expose legacy field names in your domain | ❌ Without ACL, legacy model concepts (e.g., `CustomerId` as `integer` in legacy vs `uuid` in new system) leak into your codebase and you can never get rid of them | — |
| **Queue-Based Load Leveling** | Absorb traffic bursts with a queue. Instead of processing spikes synchronously (which overwhelms downstream services), queue the work and process at a steady rate | BullMQ, SQS, RabbitMQ | Request → Queue → Worker (processes at controlled rate). Queue depth is a metric — alert when it grows beyond expected. Auto-scale workers based on queue depth | ❌ Queue adds latency — not suitable for real-time responses. Queue depth growing indefinitely = workers too slow (scale out workers). No visibility into queue = silent failures | — |
