# Frontend System Design in Next.js

> **Mental Model:** Frontend system design is about making intentional architectural decisions — *where* code runs (server/client/edge), *when* data is fetched (build/request/client), *how* state flows, and *what* fails gracefully. Every choice has a cost: performance vs freshness, simplicity vs scalability, speed vs consistency.
>

## Rendering Architecture

| Topic                                           | Core Concepts & Mental Model                                                                                                           | Key Techniques & Tools                                                           | Tradeoffs & Failure Modes                                                                                                                                                               | Real-world Examples                                                    |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **SSG** – Static Site Generation                | HTML generated once at build time, served from CDN. Fastest possible TTFB — no server involved per request                             | `fetch(url, { cache: 'force-cache' })`, `generateStaticParams` for dynamic paths | ✅ Fastest load, CDN-friendly, cheap ❌ Stale data between deploys, long build times at scale (1000s of pages), not suitable for personalized content                                     | Marketing pages, documentation, blogs, landing pages                   |
| **SSR** – Server-Side Rendering                 | HTML generated fresh on every request. Data is always current. Higher TTFB than SSG                                                    | `fetch(url, { cache: 'no-store' })`, `getServerSideProps` (Pages Router)         | ✅ Fresh data, personalized, good SEO ❌ Higher TTFB, server load scales with traffic, no CDN caching for HTML                                                                            | Personalized dashboards, news homepages, auth-gated pages              |
| **ISR** – Incremental Static Regeneration       | Static at build time, revalidated in background after N seconds or on-demand event. Stale-while-revalidate for pages                   | `next: { revalidate: 60 }`, `revalidatePath()`, `revalidateTag()`                | ✅ CDN speed + data freshness, reduced server load ❌ Users may see stale data until revalidation completes; on-demand revalidation requires a webhook or server action trigger           | E-commerce product pages, news sites, event listings                   |
| **CSR** – Client-Side Rendering                 | Minimal HTML shell, data fetched in browser after JS loads. Server never touches the data                                              | `'use client'` + TanStack Query / SWR in component                               | ✅ Rich interactivity, real-time feel, private data never touches CDN ❌ Blank screen until JS runs (bad SEO, bad slow-connection UX), hydration cost                                     | Admin panels, post-login dashboards, user-specific feeds               |
| **Streaming**                                   | Server sends HTML in chunks as components resolve. Fast shell, slow parts fill in progressively — no single slow query blocks the page | `<Suspense fallback={<Skeleton />}>`, `loading.tsx` (auto-wraps segment)         | ✅ Eliminates waterfall blocking, improves perceived performance ❌ Harder to reason about render order; skeleton abuse causes layout shift; requires careful Suspense boundary placement | Product pages (fast shell + slow reviews), AI chat responses           |
| **Partial Prerendering (PPR)** *(experimental)* | Static shell served instantly from CDN, dynamic holes stream in — single request combines SSG speed with SSR freshness                 | `experimental: { ppr: true }`, `<Suspense>` marks dynamic boundaries             | ✅ Best of SSG + SSR in one request ❌ Experimental — API may change; requires careful Suspense boundary design; not yet production-stable                                                | Product pages with static layout + dynamic pricing/stock               |
| **Server Components**                           | Components that run only on the server — zero JS sent to client, can access DB/secrets directly, cannot use hooks or browser APIs      | Default in App Router; `'use client'` opts into Client Components                | ✅ Smaller JS bundle, secure, no hydration cost ❌ No interactivity, no event handlers; Server Components cannot be imported by Client Components (only passed as `children`)             | Blog layouts, product listings, auth-aware nav shells                  |
| **Edge Computing**                              | Run code at CDN edge nodes, closest to user. Web APIs only (no Node.js, no Prisma) — ultra-low latency for lightweight logic           | `export const runtime = 'edge'`, Vercel Edge Network, Cloudflare Workers         | ✅ Lowest latency globally, scales automatically ❌ No Node.js APIs, no ORM, cold starts still possible, harder to debug, limited compute time                                            | Geo-based redirects, auth token validation, A/B testing, rate limiting |
| **Serverless Functions**                        | On-demand server execution — no persistent server process. Each Route Handler / API Route is a function                                | Next.js Route Handlers, Vercel Functions, AWS Lambda                             | ✅ Auto-scaling, pay-per-use, no server management ❌ Cold starts add latency; avoid heavy initialization per request; not suited for long-running tasks (use queues instead)             | Contact forms, webhooks, auth callbacks, scheduled cron jobs           |

## State Management Architecture

| Topic                            | Core Concepts & Mental Model                                                                                                                | Key Techniques & Tools                                                 | Tradeoffs & Failure Modes                                                                                                                                          | Real-world Examples                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| **Flux / Unidirectional Flow**   | Data flows in one direction: Action → Dispatch → Store → View. No two-way binding. Predictable, auditable state changes                     | Redux Toolkit (`createSlice`, `dispatch`), `useReducer` + `useContext` | ✅ Predictable, debuggable, time-travel ❌ Boilerplate overhead; overkill for small apps; easy to abuse (putting server state in Redux)                              | Global UI state, auth session, shopping cart, multi-step wizards                    |
| **Normalized Stores**            | Store relational data flat (like a DB) — entities indexed by ID, no duplication. `posts[id]`, `users[id]` instead of nested objects         | Redux Toolkit `createEntityAdapter`, custom selectors                  | ✅ Single source of truth per entity, efficient updates, no sync bugs ❌ More upfront design; manual denormalization for reads; unfamiliar pattern to juniors        | Posts + comments + users, products + categories, messages + senders                 |
| **Server State vs Client State** | Most "state" in apps is server data — treat it differently. Server state is async, stale, shared. Client state is synchronous, local, owned | TanStack Query / SWR (server state), Zustand / Jotai (client state)    | ✅ Correct mental model eliminates "why is my data stale?" bugs ❌ Anti-pattern: storing server responses in Redux/Zustand manually instead of using a cache library | Server: posts, users, products. Client: sidebar open/closed, modal state, form step |
| **URL as State**                 | Put shareable/bookmarkable UI state in the URL — filters, pagination, tabs, search queries. Survives refresh; shareable                     | `useSearchParams`, `useRouter`, shallow routing                        | ✅ Free persistence, shareable links, back-button works ❌ URL can get cluttered; encoding complex state is awkward; syncing with component state needs care         | Search filters, pagination page, selected tab, sort order                           |

## API Design & Data Fetching Patterns

| Topic                   | Core Concepts & Mental Model                                                                                  | Key Techniques & Tools                                                                       | Tradeoffs & Failure Modes                                                                                                                                                                         | Real-world Examples                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **REST**                | Resource-based URLs, stateless, HTTP verbs map to CRUD. Simple mental model, universal support                | Next.js Route Handlers (`GET`, `POST`, `PATCH`, `DELETE`), Axios, fetch                      | ✅ Simple, universal, cacheable GETs ❌ Over-fetching (getting fields you don't need), under-fetching (multiple roundtrips for related data), no strict contract                                    | `/api/users`, `/api/posts/[id]`, `/api/auth`                             |
| **GraphQL**             | Single endpoint, client specifies exact shape of data needed. Schema is the contract                          | Apollo Client, URQL, tRPC (type-safe alternative)                                            | ✅ No over/under-fetch, great for complex relational UIs, self-documenting schema ❌ Complexity overhead for simple apps; N+1 query problem server-side (need DataLoader); caching harder than REST | GitHub-style dashboards, nested feeds (post + author + comments + likes) |
| **tRPC**                | Type-safe RPC from client to server — no REST, no GraphQL, no codegen. TypeScript types are shared end-to-end | tRPC + Zod, Next.js adapter                                                                  | ✅ End-to-end type safety, zero schema duplication, great DX ❌ Tight client-server coupling (only works within the same TypeScript monorepo); not suitable for public APIs                         | Internal full-stack Next.js apps, team tools, admin panels               |
| **Server Actions**      | Call server functions directly from forms or Client Components — no API route needed for mutations            | `'use server'` directive, `useFormState` / `useActionState`, `revalidatePath`                | ✅ Eliminates boilerplate API routes for mutations, progressive enhancement for forms ❌ Not a replacement for public APIs; harder to reuse across services; error handling requires care           | Form submissions, CRUD mutations, cart updates, profile edits            |
| **Pagination — Offset** | Fetch page N with skip/limit. Simple to implement and understand                                              | `?page=2&limit=20`, `OFFSET` in SQL                                                          | ✅ Simple, supports jumping to arbitrary page ❌ Inconsistent with real-time data (inserts/deletes shift pages), performance degrades on high offsets (DB must scan all skipped rows)               | E-commerce product grids, search results                                 |
| **Pagination — Cursor** | Fetch next N items after a stable cursor (ID or timestamp). Consistent for real-time feeds                    | `?cursor=<lastId>`, Prisma `cursor`, TanStack Query `useInfiniteQuery`                       | ✅ Consistent, performant at scale, works with real-time inserts ❌ Cannot jump to arbitrary page; cursor must be stable (use unique ID, not offset)                                                | Twitter/Instagram feeds, chat history, infinite scroll                   |
| **Batching**            | Combine multiple data requests into one round trip. Reduces waterfall and connection overhead                 | React's automatic RSC batching, DataLoader (server-side), `Promise.all` for parallel fetches | ✅ Fewer round trips, lower latency ❌ Added complexity; over-batching can delay fast responses waiting for slow ones                                                                               | Profile + settings + activity feed in one SSR render                     |
| **Optimistic Updates**  | Update UI instantly before server confirms. Rollback on failure                                               | TanStack Query `onMutate` + `onError` rollback, SWR mutate                                   | ✅ Instant-feeling UX ❌ Rollback UX can be jarring; must handle conflict when server disagrees (e.g., someone else deleted the item); not suitable for critical transactions                       | Like/unlike, follow/unfollow, cart add/remove, drag-and-drop reorder     |

## Real-time & Async Patterns

| Topic                             | Core Concepts & Mental Model                                                                                         | Key Techniques & Tools                                                      | Tradeoffs & Failure Modes                                                                                                                                                                                            | Real-world Examples                                                                                 |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| **Short Polling**                 | Client repeatedly asks server "any updates?" on a fixed interval                                                     | `setInterval` + `fetch`, TanStack Query `refetchInterval`                   | ✅ Simple, works everywhere ❌ Wasteful — constant requests even when nothing changed; high server load at scale; not suitable for >100 concurrent users needing low latency                                           | Low-frequency status checks, build progress indicators                                              |
| **Long Polling**                  | Client sends request, server holds it open until there's data to return (or timeout)                                 | Custom server endpoint, held HTTP response                                  | ✅ Lower latency than short polling, no persistent connection needed ❌ Server must hold many open connections; reconnect logic required; more complex than short polling                                              | Order status updates, ticket queue notifications                                                    |
| **SSE (Server-Sent Events)**      | Persistent one-way stream from server to client over HTTP. Built-in reconnection                                     | `EventSource` API, Next.js Route Handler returning `ReadableStream`         | ✅ Simple, HTTP-only (no upgrade), auto-reconnect, works through proxies ❌ Server → client only (no client → server on same connection); max 6 connections per domain in HTTP/1.1                                     | Live logs, streaming AI responses (ChatGPT-style), live sports scores                               |
| **WebSockets**                    | Full-duplex persistent TCP connection. Both sides can send at any time                                               | Socket.io, native `WebSocket` API, Pusher, Ably (hosted)                    | ✅ Lowest latency bidirectional communication ❌ Custom Next.js server or external service required (Vercel serverless doesn't support persistent WebSocket connections natively); reconnect and auth logic complexity | Chat apps, collaborative editors, live trading, multiplayer games                                   |
| **Debounce & Throttle**           | Control rate of expensive operations triggered by user input. Debounce: wait for pause. Throttle: cap at N calls/sec | `lodash.debounce`, `lodash.throttle`, custom `useDebounce` hook             | ❌ Common mistake: debouncing the wrong thing (debounce the API call, not the input handler); too-long debounce feels laggy; too-short defeats the purpose                                                            | Search-as-you-type (debounce), scroll/resize handlers (throttle), button spam prevention (throttle) |
| **Retries with Backoff + Jitter** | Retry failed requests with exponentially increasing delays + random jitter. Prevents thundering herd on recovery     | TanStack Query `retry` + `retryDelay`, custom exponential backoff           | ✅ Handles transient failures gracefully ❌ Without jitter, all clients retry simultaneously (thundering herd); retrying non-idempotent operations (POST) can cause duplicates — use idempotency keys                  | Rate-limited API calls, flaky third-party services, payment webhooks                                |
| **Race Conditions**               | Multiple async operations in flight — stale response overwrites fresh one                                            | `AbortController`, TanStack Query (handles internally), request ID tracking | ❌ Classic bug: type fast in search box, slow request from 3 keystrokes ago resolves after fast request from 5 keystrokes → shows wrong results                                                                       | Search filters, fast navigation, tab switching with async data                                      |
| **Long-running Tasks**            | Never block an HTTP request with heavy work. Offload to a queue or background worker                                 | BullMQ + Redis, Upstash QStash, Vercel Cron, Inngest, Temporal              | ✅ Request returns immediately, work happens async ❌ Need observability (job status, failure visibility); user needs a way to know when it's done (SSE/polling for status)                                            | Email sending, PDF generation, video processing, AI batch jobs, report generation                   |
| **Offline & PWA**                 | Cache critical assets and data for offline use. Sync changes when reconnection happens                               | Service Worker, Workbox, `next-pwa`, IndexedDB, Background Sync API         | ✅ Works without connectivity, app-like install experience ❌ Cache invalidation is hard; IndexedDB API is low-level (use Dexie.js); conflict resolution on sync is complex                                            | Field service apps, note-taking apps, delivery tracking                                             |

## Performance Architecture

| Topic                             | Core Concepts & Mental Model                                                                                                                                           | Key Techniques & Tools                                                                                                                                                      | Tradeoffs & Failure Modes                                                                                                                                                                                      | Real-world Examples                                                                                        |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Core Web Vitals**               | Google's three user-centric performance metrics that affect search ranking. Measure real-user experience, not synthetic lab scores                                     | **LCP** (load speed — largest content painted), **INP** (interactivity — replaces FID), **CLS** (layout stability). Chrome UX Report (CrUX), Lighthouse, PageSpeed Insights | ✅ Direct SEO impact + real UX signal ❌ Common mistakes: no `priority` on hero image (hurts LCP), injecting content above the fold without reserved space (hurts CLS), long main-thread tasks (hurts INP)       | LCP: hero image. INP: search input response. CLS: images without `width`/`height`, ads injected above fold |
| **Critical Rendering Path**       | Browser must parse HTML → build DOM → load CSS (render-blocking) → build CSSOM → build Render Tree → Layout → Paint. Every render-blocking resource delays first paint | Preload (`<link rel="preload">`), defer/async scripts, inline critical CSS, `next/font`                                                                                     | ❌ Render-blocking CSS/JS is the most common performance killer in production; too many `rel="preload"` hints compete with each other                                                                           | Inline above-the-fold CSS, defer analytics scripts, preload hero font                                      |
| **Code Splitting & Lazy Loading** | Don't ship code the user hasn't asked for yet. Route-level splitting is highest ROI                                                                                    | `React.lazy` + `Suspense`, `next/dynamic`, dynamic `import()`                                                                                                               | ✅ Smaller initial bundle, faster TTI ❌ Lazy loading everything creates many small requests; components loaded on interaction have a delay — preload on hover to mitigate                                       | Load rich text editor only when user clicks "Write", load chart library on dashboard tab                   |
| **Bundle Optimization**           | Every KB of JS has a parse + execution cost, not just download cost                                                                                                    | Webpack Bundle Analyzer, `@next/bundle-analyzer`, Bundlephobia, tree shaking                                                                                                | ❌ Barrel files (`index.ts` re-exporting everything) defeat tree shaking; importing full lodash instead of individual functions; duplicate packages from version mismatches                                     | `import { debounce } from 'lodash'` ❌ vs `import debounce from 'lodash/debounce'` ✅                        |
| **Caching Strategy**              | Multi-layer caching: CDN → Next.js fetch cache → browser cache. Each layer has different TTL and invalidation mechanisms                                               | CDN cache headers (`Cache-Control`, `s-maxage`), Next.js fetch cache (`revalidate`), browser cache (`stale-while-revalidate`), SWR/TanStack Query                           | ❌ Most common mistake: not caching what should be cached (every SSR hit goes to origin), or caching personalized responses (CDN serves wrong user's data)                                                      | Static assets: `max-age=31536000, immutable`. API responses: `s-maxage=60, stale-while-revalidate=3600`    |
| **List Virtualization**           | Only render DOM nodes currently visible in the viewport. 10,000 row list renders only ~20 nodes                                                                        | react-window (`FixedSizeList`, `VariableSizeList`), TanStack Virtual, react-virtuoso                                                                                        | ✅ Keeps DOM lightweight regardless of data size ❌ Accessibility concerns (screen readers struggle with virtualized lists); dynamic row heights require measured virtualization; breaks `Ctrl+F` in-page search | Social media feeds, data tables, chat history, autocomplete dropdowns                                      |
| **Preload & Prefetch**            | Fetch resources before the user explicitly requests them — instant-feeling navigation                                                                                  | `<Link prefetch>` (prefetches on viewport entry), `Image priority` (preloads LCP image), `rel="preload"` for fonts/critical assets                                          | ❌ Over-prefetching wastes bandwidth (especially on mobile); prefetching should be based on likely navigation, not everything; too many preload hints compete and cancel gains                                  | Prefetch next page on hover, priority on hero image, preload critical web font                             |
| **Adaptive Loading**              | Serve different experiences based on device capability and network quality                                                                                             | `navigator.connection` API, `navigator.deviceMemory`, `navigator.hardwareConcurrency`                                                                                       | ✅ Better experience for low-end users ❌ Network API not available in all browsers; hard to test; requires separate code paths                                                                                  | Lower image quality on slow connections, defer heavy animations on low-memory devices                      |
| **Compression**                   | Reduce transfer size of text assets (JS, CSS, HTML) and media                                                                                                          | Brotli (better compression than gzip, supported by all modern browsers), gzip (fallback), WebP/AVIF for images                                                              | ✅ Significant transfer size reduction (Brotli: ~20% better than gzip) ❌ CPU cost for compression (mitigated by CDN/pre-compression); Brotli only via HTTPS; image formats need fallback for old browsers       | CDN-level Brotli for all text assets, AVIF with WebP fallback via `<picture>`                              |

## Image & Media Optimization

| Topic                  | Core Concepts & Mental Model                                                                                                                                           | Key Techniques & Tools                                                                                                   | Tradeoffs & Failure Modes                                                                                                                                                                    | Real-world Examples                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **`next/image`**       | Automatic format conversion (WebP/AVIF), responsive `srcset`, lazy loading, prevents CLS by enforcing dimensions. On-demand CDN transforms via Vercel or custom loader | `<Image>`, `priority`, `fill`, `sizes`, `loader` prop                                                                    | ❌ Forgetting `priority` on LCP image (biggest single cause of poor LCP); missing `sizes` prop causes over-large image downloads; `fill` requires positioned parent                           | `priority` on hero/above-fold. `loading="lazy"` (default) on gallery images                                 |
| **Image Formats**      | AVIF > WebP > JPEG/PNG for photos. SVG for icons/logos/illustrations. Each has browser support tradeoffs                                                               | `<picture>` with `<source type="image/avif">` fallback to WebP fallback to JPEG; `next/image` handles this automatically | ❌ AVIF encoding is slow (build-time tradeoff); don't use raster for icons — SVG scales losslessly and is smaller                                                                             | Hero photos: AVIF/WebP. Icons: inline SVG. Logos: SVG. Screenshots: WebP                                    |
| **Responsive Images**  | Serve correctly sized image per viewport — a mobile user should not download a 2000px image                                                                            | `sizes` prop, `srcset`, `<picture>` with art direction                                                                   | ❌ Most common mistake: omitting `sizes` attribute — browser downloads full-size image for every viewport                                                                                     | `sizes="(max-width: 768px) 100vw, (max-width: 1200px) 50vw, 33vw"`                                          |
| **Alt Text**           | Describes image purpose to screen readers and search engines. Decorative images use empty `alt=""`                                                                     | Standard HTML `alt` attribute                                                                                            | ❌ Missing alt = accessibility failure + SEO penalty; don't describe the image literally ("image of...") — describe its purpose in context; empty alt for decorative images (not missing alt) | Product: "Red Nike Air Max 90, side view". Chart: "Revenue growth Q1-Q4 2024". Decorative divider: `alt=""` |
| **Image CDN**          | Transform, cache, and serve images at the edge — resize, crop, format-convert on the fly                                                                               | `next/image` (Vercel CDN), Cloudinary, Imgix, ImageKit                                                                   | ✅ Device-appropriate sizes, CDN caching, format negotiation ❌ External CDN adds vendor dependency; Cloudinary URL transforms expose transformation logic in URLs                             | Product images served from Cloudinary with on-the-fly crop and format                                       |
| **Video Optimization** | Video is the largest asset type. Unoptimized video is the single biggest bandwidth cost on most marketing sites                                                        | FFmpeg (compress, strip audio from muted videos), Cloudinary Video, HLS streaming                                        | ❌ Biggest mistake: autoplay video with audio on mobile (blocked by browsers); MP4 only without modern formats; no `preload="none"` for below-fold videos                                     | Hero video: muted, compressed, `preload="metadata"`. Long-form content: HLS streaming                       |

## Reliability Patterns

| Topic                      | Core Concepts & Mental Model                                                                                     | Key Techniques & Tools                                                                                               | Tradeoffs & Failure Modes                                                                                                                                                  | Real-world Examples                                                                    |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **Error Boundaries**       | Catch render errors in a component subtree and show a fallback instead of crashing the whole app                 | `react-error-boundary`, `componentDidCatch`                                                                          | ❌ Error boundaries don't catch: async errors in event handlers, errors in effects, errors in the boundary itself; nest multiple boundaries — one per major feature section | Per-route boundary, per-widget boundary in dashboards                                  |
| **User Experience States** | Every async operation has 5 states: idle, loading, success, error, empty. Design all five                        | Skeleton screens (loading), toast/inline error (error), empty state illustration (empty), `<Suspense>` for streaming | ❌ Most apps only design success state; missing empty state makes users think it's broken; global error messages are useless ("Something went wrong" with no action)        | Skeleton for loading lists, empty state for zero results, retry button on error        |
| **Timeouts**               | Every external fetch needs a timeout — SSR fetch hanging = request hangs = user waits forever                    | `AbortController` + `setTimeout`, `signal` option on `fetch`                                                         | ❌ No timeout in SSR fetch = one slow upstream API can make your entire page response slow; set aggressive timeouts (1-3s) with fallback content                            | `const controller = new AbortController(); setTimeout(() => controller.abort(), 3000)` |
| **Race Conditions**        | Async results arrive out of order — stale response from slow request overwrites fresh response from fast request | `AbortController` to cancel previous request, TanStack Query (handles automatically), cleanup in `useEffect`         | ❌ Classic `useEffect` bug — user types "a", "ab", "abc" — "ab" response arrives after "abc" response — shows wrong results                                                 | Search-as-you-type, fast route navigation, tab switching                               |

## Security Architecture

| Topic                                 | Core Concepts & Mental Model                                                                                      | Key Techniques & Tools                                                                               | Tradeoffs & Failure Modes                                                                                                                                                                     | Real-world Examples                                                                                                                      |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **XSS (Cross-Site Scripting)**        | Attacker injects malicious script into your page via user-generated content. Runs with your origin's privileges   | DOMPurify (sanitize HTML), avoid `dangerouslySetInnerHTML`, CSP headers                              | ❌ `innerHTML` with unsanitized user input = XSS. React's JSX escapes by default — only dangerous when you bypass it deliberately                                                              | Sanitize user bio/comments, set `Content-Security-Policy` header                                                                         |
| **CSRF (Cross-Site Request Forgery)** | Malicious site tricks authenticated user's browser into making requests to your API                               | `SameSite=Strict` cookies, CSRF tokens, verify `Origin`/`Referer` header on mutations                | ❌ `SameSite=Lax` (default) protects most cases but not all; APIs with `SameSite=None` without CSRF tokens are vulnerable                                                                      | NextAuth handles CSRF automatically; custom APIs need CSRF token validation                                                              |
| **Security Headers**                  | HTTP response headers that instruct browsers on security policy — prevent entire classes of attacks               | `next.config.js` `headers()` function, Helmet-equivalent config                                      | ❌ Missing `X-Frame-Options: DENY` = clickjacking vulnerability; missing `HSTS` = protocol downgrade attacks; too strict CSP breaks third-party integrations                                   | `Content-Security-Policy`, `X-Frame-Options`, `HSTS`, `X-Content-Type-Options`, `Referrer-Policy`                                        |
| **Auth vs Authorization**             | Auth = who are you. Authorization = what are you allowed to do. Commonly confused                                 | Auth: Auth.js / Clerk. Authorization: middleware + role checks in Server Components / Route Handlers | ❌ Checking authorization only in UI (hiding a button) is not authorization — always enforce on the server; middleware is good for coarse route protection, not fine-grained data-level access | Route middleware: redirect unauthenticated. Server Component: check role before rendering data. Route Handler: re-verify before mutation |
| **API Authentication**                | Identify the caller of your API. Different patterns for different callers (browser session vs machine-to-machine) | Session cookies (browser users), JWT Bearer tokens (SPAs, mobile), API keys (server-to-server)       | ❌ Never put secrets in client-side code (`NEXT_PUBLIC_` prefix); JWTs are not sessions — they can't be revoked until expiry without a blocklist; API keys need rotation and scoping           | NextAuth session cookies for web app; API key for webhook consumers; JWT for mobile app                                                  |
| **Rate Limiting**                     | Prevent API abuse, brute-force attacks, and cost overruns on serverless                                           | Upstash Rate Limit, Vercel Edge middleware, `@upstash/ratelimit`                                     | ❌ Per-IP rate limiting is bypassable with IP rotation; rate limit by user ID when authenticated; return `Retry-After` header to help legitimate clients back off                              | Login endpoint: 5 attempts/minute. API: 100 req/min per user. Public endpoint: 20 req/min per IP                                         |

## Scalability & Infrastructure Patterns

| Topic                     | Core Concepts & Mental Model                                                                                            | Key Techniques & Tools                                                          | Tradeoffs & Failure Modes                                                                                                                                                                                   | Real-world Examples                                                                   |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| **Micro-frontends**       | Split large frontend into independently deployable pieces owned by different teams. Architectural choice, not a library | Module Federation (Webpack 5), iframes (simple isolation), single-spa           | ✅ Independent deploys, team autonomy, tech heterogeneity ❌ Shared state is complex, CSS isolation is painful, increased operational overhead, premature optimization for most teams — start with a monolith | Large org: Shell app + checkout app + catalog app deployed independently              |
| **Monorepo**              | Single repo for multiple apps/packages — share UI components, types, utilities, config across projects                  | Turborepo *(recommended)*, Nx, `pnpm` workspaces                                | ✅ Easy code sharing, single PR for cross-project changes ❌ Build tooling complexity, repo size growth; need proper `turbo.json` pipeline config for caching                                                 | `apps/web`, `apps/admin`, `packages/ui`, `packages/types`                             |
| **CI/CD Pipeline**        | Automated pipeline: lint → type-check → test → build → deploy. Catches issues before production                         | GitHub Actions, Vercel Preview Deployments, Turborepo Remote Cache              | ❌ Skipping type-check in CI (passes locally, breaks in prod); not running `next build` in CI (runtime errors at deploy); no preview environments (testing on prod)                                          | `pnpm lint && tsc --noEmit && pnpm test && next build` in CI                          |
| **Environment Variables** | Separate config from code. Three environments: development, staging, production. Never commit secrets                   | `.env.local`, `.env.production`, Vercel env dashboard, Doppler (secret manager) | ❌ `NEXT_PUBLIC_` variables are embedded in the client bundle — never put secrets there; `.env.local` should never be committed; rotate secrets regularly                                                    | `NEXT_PUBLIC_API_URL` (safe, client-side). `DATABASE_URL` (server-only, never public) |

## Accessibility & i18n

| Topic                           | Core Concepts & Mental Model                                                                                                                         | Key Techniques & Tools                                                     | Tradeoffs & Failure Modes                                                                                                                                                                                                          | Real-world Examples                                                                                  |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **Accessibility (a11y)**        | 15-20% of users have some disability. Semantic HTML is the foundation — ARIA supplements when native semantics are insufficient, never replaces them | axe-core, `jest-axe`, Lighthouse a11y audit, NVDA/VoiceOver manual testing | ❌ Using `<div onClick>` instead of `<button>` = keyboard inaccessible; adding ARIA without understanding it often makes things worse; automated tools only catch ~30% of issues — manual keyboard + screen reader testing required | `<button>` not `<div onClick>`, `aria-live` for dynamic content, focus trap in modals, skip-nav link |
| **Internationalization (i18n)** | Localize text, date/number formats, and layout direction (LTR/RTL). Design for text expansion (German is ~30% longer than English)                   | `next-intl`, `i18next`, native `Intl` API (dates/numbers/plurals)          | ❌ Hardcoded strings in components, text in images (can't translate), assuming LTR layout, formatting dates with `toLocaleDateString()` without locale param                                                                        | `app/[locale]/page.tsx`, `Intl.NumberFormat` for currency, `dir="rtl"` for Arabic/Hebrew             |
