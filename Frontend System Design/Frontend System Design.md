## Networking — API Paradigms

| Topic       | Core Concepts & Mental Model                                                                                                                                                                | Tools & Libraries                                                   | Key Techniques                                                                                                                                       | Tradeoffs & Failure Modes                                                                                                                                                                                                                                       | Resources                                                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **REST**    | Resources identified by URLs, stateless, HTTP verbs map to CRUD. Simplest API contract — universally understood. Cacheable by nature (GET)                                                  | Postman, Thunder Client, Swagger/OpenAPI, Axios, fetch              | Proper verb usage (`GET`/`POST`/`PUT`/`PATCH`/`DELETE`), status codes (2xx/4xx/5xx), versioning (`/api/v1/`), pagination, filtering via query params | ✅ Simple, universal, CDN-cacheable GETs ❌ Over-fetching (getting fields you don't need), under-fetching (N+1 trips for related data), no strict type contract between client/server                                                                             | [RESTful API Design](https://restfulapi.net/), [HTTP Status Codes](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status) |
| **GraphQL** | Single endpoint, client declares exact data shape needed. Schema is a typed contract shared by client and server. Eliminates over/under-fetching                                            | Apollo Client, URQL, GraphQL Playground, Apollo Studio              | Queries (read), mutations (write), subscriptions (real-time), fragments for reuse, `DataLoader` (server-side) to solve N+1, persisted queries        | ✅ Client controls shape, great for nested/relational UIs, self-documenting schema ❌ N+1 query problem server-side if not using DataLoader; caching harder than REST (non-GET); complexity overhead for simple CRUD; large queries can be expensive              | [GraphQL.org](https://graphql.org/learn), [Apollo Client docs](https://www.apollographql.com/docs/react)                     |
| **gRPC**    | Binary protocol using Protocol Buffers. Strongly typed IDL-defined contracts, streaming support. **Not natively browser-compatible** — requires gRPC-Web proxy or Envoy sidecar on frontend | gRPC-Web, Protobuf, Envoy proxy                                     | Unary, server/client/bidirectional streaming, `.proto` schema as single source of truth for types, code generation for clients                       | ✅ Extremely fast (binary, compressed), strong typing via Protobuf, native streaming ❌ Not usable directly in browser without gRPC-Web + proxy layer; harder to debug than REST (binary not human-readable); limited browser support; overkill for most web apps | [gRPC-Web](https://grpc.io/docs/platforms/web), [Protobuf docs](https://protobuf.dev/)                                       |
| **tRPC**    | Type-safe RPC — call server functions from client with full TypeScript type inference. No schema, no codegen, no REST URLs. Types flow end-to-end automatically                             | tRPC v11+, Zod (input validation), TanStack Query (transport layer) | Routers + procedures (query/mutation), Zod schemas for input validation, context for auth/session, middleware on procedures, Next.js adapter         | ✅ Zero type duplication, best-in-class DX for TypeScript monorepos, no API contract drift ❌ Tight client-server coupling (same TypeScript repo required); not suitable for public APIs or non-TypeScript consumers; not REST — can't be called from Postman     | [tRPC docs](https://trpc.io/docs)                                                                                            |

## Communication Patterns

| Topic                        | Core Concepts & Mental Model                                                                                                        | Tools & Libraries                                                                                             | Key Techniques                                                                                                                                                     | Tradeoffs & Failure Modes                                                                                                                                                                                                                                                    | Resources                                                                                                                                                       |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Short Polling**            | Client asks server "any updates?" on a fixed interval. Simple to implement. Server always responds immediately (empty or with data) | `setInterval` + `fetch`, TanStack Query `refetchInterval`                                                     | Fixed interval (e.g. 5s), exponential backoff on error, stop polling on component unmount/tab hidden                                                               | ✅ Works everywhere, simple ❌ Wasteful — sends requests even when nothing changed; server load grows linearly with users; not suitable for low-latency or high-frequency scenarios                                                                                            | —                                                                                                                                                               |
| **Long Polling**             | Client sends request, server holds it open until it has data to return (or timeout). Then client immediately re-requests            | Custom Node.js endpoint with delayed response                                                                 | Server holds response via async timeout, client loops on response, timeout + reconnect strategy required                                                           | ✅ Lower latency than short polling, no persistent connection ❌ Server must hold many concurrent open connections; reconnect logic adds complexity; harder to scale behind load balancers                                                                                     | —                                                                                                                                                               |
| **Server-Sent Events (SSE)** | Persistent one-way HTTP stream: server → client. Uses standard HTTP (not a new protocol). Browser auto-reconnects on disconnect     | `EventSource` API (native), Next.js Route Handler returning `ReadableStream`, `@microsoft/fetch-event-source` | Named event types (`event: message`), `data:` field, `id:` for reconnect cursor, `retry:` for reconnect interval, route handler: `return new Response(stream)`     | ✅ Simple, HTTP-only, auto-reconnect built-in, works through proxies/firewalls ❌ Server → client only; max 6 connections per domain on HTTP/1.1 (use HTTP/2); Vercel/serverless functions time out — use streaming or dedicated SSE server                                    | [MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events), [EventSource API](https://developer.mozilla.org/en-US/docs/Web/API/EventSource) |
| **WebSockets**               | Full-duplex persistent TCP connection. Both sides send messages at any time. Requires HTTP → WS upgrade handshake                   | Socket.io (abstraction + fallback), native `WebSocket` API, Pusher/Ably/PartyKit (hosted)                     | Event-based messaging, rooms/namespaces (Socket.io), auth via handshake query/cookie, heartbeat/ping-pong for connection health, reconnection with backoff         | ✅ Lowest latency bidirectional communication ❌ Vercel/AWS Lambda serverless don't support persistent WS natively — use hosted service or dedicated server; reconnect + auth state management is complex; stateful connections don't scale horizontally without Redis pub/sub | [Socket.io docs](https://socket.io/docs), [MDN WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket)                                           |
| **Webhooks**                 | Server-to-server HTTP callbacks. External service calls *your* endpoint when an event occurs. Asynchronous, event-driven            | ngrok (local testing), Svix (webhook platform), Express/Next.js Route Handler                                 | Verify payload signature (HMAC `X-Signature` header), idempotency (process same event twice safely), respond `200` fast then process async (queue), retry handling | ✅ Decoupled, async, no polling ❌ No delivery guarantee without retry logic on sender side; your endpoint must be publicly reachable (problem in dev — use ngrok); replay attacks if signature not verified; timeouts if processing is slow                                   | [Stripe Webhook Guide](https://stripe.com/docs/webhooks)                                                                                                        |

## Security

> **Mental Model:** Security is defence in depth — multiple layers. No single technique is sufficient. Frontend security focuses on: (1) protecting the DOM, (2) protecting the network, (3) protecting storage, (4) protecting the user's identity.
> 

| Topic                                    | Core Concepts & Mental Model                                                                                                                                                                                             | Tools & Libraries                                                           | Key Techniques                                                                                                                                                                                                        | Tradeoffs & Failure Modes                                                                                                                                                                                                          | Resources                                                                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **XSS (Cross-Site Scripting)**           | Attacker injects malicious script via user-generated content. Runs with full origin privileges. Three types: Stored (in DB), Reflected (in URL), DOM-based (client-side JS)                                              | DOMPurify (sanitize HTML), `Content-Security-Policy` header                 | Sanitize before rendering user HTML (`DOMPurify.sanitize()`), avoid `dangerouslySetInnerHTML`, set strict CSP header, encode output (React JSX does this by default)                                                  | ❌ React's JSX escapes by default — only dangerous when you bypass it (`dangerouslySetInnerHTML`, `eval`, `innerHTML`). DOM-based XSS comes from `document.write`, `location.href = userInput`, etc.                                | [OWASP XSS](https://owasp.org/www-community/attacks/xss), [DOMPurify](https://github.com/cure53/DOMPurify)                |
| **CSRF (Cross-Site Request Forgery)**    | Attacker tricks authenticated user's browser into making requests to your server using stored cookies. Exploits the browser's automatic cookie-sending behavior                                                          | —                                                                           | `SameSite=Strict` or `SameSite=Lax` on session cookies, anti-CSRF token in form/header, validate `Origin`/`Referer` header on mutations, CAPTCHA for critical actions, avoid state-changing `GET` requests            | ❌ `SameSite=Lax` (browser default) doesn't protect against top-level cross-site `POST`. `SameSite=Strict` can break OAuth flows. JWT in `Authorization` header is CSRF-immune (not auto-sent by browser)                           | [OWASP CSRF](https://owasp.org/www-community/attacks/csrf)                                                                |
| **CORS (Cross-Origin Resource Sharing)** | Browser enforces same-origin policy — blocks cross-origin requests by default. CORS headers tell the browser which origins, methods, and headers are allowed                                                             | `cors` npm package (Node), browser DevTools Network tab                     | Configure `Access-Control-Allow-Origin` (never `*` with credentials), `Access-Control-Allow-Methods`, preflight (`OPTIONS`) handling, `credentials: 'include'` only when necessary                                    | ❌ Common mistake: setting `Access-Control-Allow-Origin: *` with `Access-Control-Allow-Credentials: true` — browsers reject this. CORS is a browser protection, not a server security measure — server-to-server requests ignore it | [MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS)                                                        |
| **Content Security Policy (CSP)**        | HTTP response header that tells the browser which sources are trusted for scripts, styles, images, frames, etc. Prevents XSS by refusing to execute untrusted scripts                                                    | CSP Evaluator (Google), `next.config.js` headers, `helmet` (Node)           | `script-src 'self'` (no inline scripts), `object-src 'none'`, `base-uri 'self'`, report-only mode for testing (`Content-Security-Policy-Report-Only`), nonce-based for inline scripts                                 | ❌ Too strict CSP breaks third-party integrations (analytics, chat widgets); `'unsafe-inline'` defeats XSS protection; start with report-only mode and tighten gradually                                                            | [MDN CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/CSP), [CSP Evaluator](https://csp-evaluator.withgoogle.com/)  |
| **Security Headers**                     | HTTP response headers that instruct browsers on security policies. One of the highest-ROI security improvements — add in `next.config.js` or CDN config                                                                  | `next.config.js` `headers()`, `helmet` (Express), securityheaders.com       | `X-Frame-Options: DENY` (clickjacking), `X-Content-Type-Options: nosniff` (MIME sniffing), `Strict-Transport-Security` (HSTS — force HTTPS), `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` | ❌ Missing `X-Frame-Options` = clickjacking. Missing HSTS = protocol downgrade attack. Wrong `Referrer-Policy` leaks sensitive URL paths to third parties                                                                           | [securityheaders.com](https://securityheaders.com/), [OWASP Secure Headers](https://owasp.org/www-project-secure-headers) |
| **Clickjacking & iframe Security**       | Attacker embeds your page in an invisible iframe on their site and tricks user into clicking elements                                                                                                                    | —                                                                           | `X-Frame-Options: DENY` or `SAMEORIGIN`, CSP `frame-ancestors 'none'`, `sandbox` attribute on iframes you embed (`sandbox="allow-scripts allow-same-origin"`)                                                         | ❌ `X-Frame-Options` is deprecated in favor of CSP `frame-ancestors` — set both for compatibility                                                                                                                                   | [MDN X-Frame-Options](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/X-Frame-Options)                          |
| **Subresource Integrity (SRI)**          | Ensures external scripts/styles (from CDN) haven't been tampered with by verifying a cryptographic hash. If CDN is compromised, the browser refuses the resource                                                         | [srihash.org](https://www.srihash.org/)                                     | Add `integrity="sha384-<hash>"` + `crossorigin="anonymous"` on external `<script>` and `<link>` tags                                                                                                                  | ❌ Hash must be updated whenever the external resource version changes; doesn't protect dynamically loaded scripts (only static URLs); not needed if you self-host all assets                                                       | [MDN SRI](https://developer.mozilla.org/en-US/docs/Web/Security/Subresource_Integrity)                                    |
| **Permissions Policy**                   | HTTP response header that controls which browser features (camera, microphone, geolocation) a page or its iframes can use. Replaced Feature Policy                                                                       | `res.setHeader("Permissions-Policy", ...)`, DevTools → Application → Frames | `Permissions-Policy: geolocation=(self), camera=(), microphone=()` — empty `()` = denied for everyone including self. `(self)` = allowed only for your origin                                                         | ❌ Permissions Policy only restricts browser APIs, not server-side operations. Not supported in all browsers                                                                                                                        | [MDN Permissions Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Permissions_Policy)                            |
| **Input Validation & Sanitization**      | Validate on both client (UX feedback) and server (security). Client-side validation is for convenience, never for trust                                                                                                  | Zod, Yup, React Hook Form, DOMPurify                                        | Type (`string`, `email`, `number`), format (regex), range (`min`/`max`), required fields. Sanitize HTML before display, never before storage (store raw, sanitize on output)                                          | ❌ Sanitizing before storing and then sanitizing again on display = double-sanitization corruption. Client-side validation only = bypassable with DevTools/curl. Never trust `Content-Type` header alone                            | [Zod docs](https://zod.dev/)                                                                                              |
| **Dependency Security**                  | Third-party npm packages are a supply chain attack vector. Regular auditing is a production hygiene practice                                                                                                             | `npm audit`, `pnpm audit`, Snyk, Socket.dev, Renovate (auto-updates)        | Run `npm audit --audit-level=high` in CI, use `package-lock.json` / `pnpm-lock.yaml` (lockfiles prevent version drift), pin major versions of critical packages                                                       | ❌ `npm install` without lockfile = gets latest (possibly compromised) version; `node_modules` is 3rd-party code running with full privileges; typosquatting (e.g. `reakt` instead of `react`)                                      | [Socket.dev](https://socket.dev/), [npm audit docs](https://docs.npmjs.com/cli/v10/commands/npm-audit)                    |
| **HTTPS & Transport Security**           | All production traffic must be HTTPS. Mixed content (HTTP resource on HTTPS page) is blocked by browsers. HSTS prevents downgrade attacks                                                                                | Vercel (auto HTTPS), Let's Encrypt, Cloudflare                              | Enable HSTS (`Strict-Transport-Security: max-age=31536000; includeSubDomains`), redirect HTTP→HTTPS at CDN/server level, fix mixed content warnings, `Secure` flag on cookies                                         | ❌ Including subdomains in HSTS is permanent — misconfigured subdomain bricks it. Never preload HSTS without testing thoroughly                                                                                                     | [MDN HSTS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Strict-Transport-Security)                           |
| **SSRF Awareness** *(System Design)*     | Server-Side Request Forgery — attacker causes your backend to fetch an unintended internal/external URL (e.g., AWS metadata endpoint `169.254.169.254`). Frontend devs need to understand this for system design reviews | Burp Suite, OWASP ZAP                                                       | Frontend design responsibility: never send raw user-provided URLs to server-side fetch without validation; backend must whitelist allowed domains/protocols                                                           | ❌ A frontend input field that sends a user-provided URL to a server-side fetch (e.g., "paste any URL to preview") is a classic SSRF vector                                                                                         | [OWASP SSRF](https://owasp.org/www-community/attacks/Server_Side_Request_Forgery)                                         |
| **Storage Security**                     | Different storage mechanisms have different security characteristics. Choosing the wrong one exposes tokens to XSS or CSRF                                                                                               | Chrome DevTools → Application tab                                           | `HttpOnly` + `Secure` cookies (not readable by JS — XSS-safe) for session tokens. Avoid storing JWTs in `localStorage` (readable by JS — XSS-vulnerable). `sessionStorage` for ephemeral state                        | ❌ Most common mistake: storing JWT access tokens in `localStorage` for "convenience" — any XSS steals all tokens permanently. Use `HttpOnly` cookie + short-lived access token instead                                             | [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)            |

## Browser Storage & Caching

| Topic                         | Core Concepts & Mental Model                                                                                                                                       | Tools & Libraries                                                              | Key Techniques                                                                                                                                                                                            | Tradeoffs & Failure Modes                                                                                                                                                                                                  | Resources                                                                                                                                               |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`localStorage`**            | Key-value string storage. Persists across browser sessions and tabs. Synchronous (blocks main thread for large data)                                               | `localStorage` API                                                             | Store non-sensitive user preferences (theme, language). Always serialize with `JSON.stringify/parse`. Check storage quota (~5MB)                                                                          | ❌ Synchronous reads block main thread; accessible to all JS on the page (XSS risk); no expiry mechanism — you must implement TTL manually; not suitable for sensitive data                                                 | [MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)                                                                |
| **`sessionStorage`**          | Same API as `localStorage` but data is cleared when the tab closes. Isolated per tab                                                                               | `sessionStorage` API                                                           | Ephemeral state that should not persist: wizard form progress, temp search filters, one-time tokens                                                                                                       | ❌ Not shared across tabs — cannot use for cross-tab communication; lost on refresh in some cases; same XSS risk as localStorage                                                                                            | [MDN sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)                                                            |
| **Cookies**                   | Small key-value strings sent with every HTTP request automatically by the browser. The only storage type that participates in HTTP                                 | `document.cookie` (avoid), `js-cookie` library, server-set `Set-Cookie` header | `HttpOnly` (not readable by JS), `Secure` (HTTPS only), `SameSite=Strict/Lax`, `Expires`/`Max-Age`, `Path` scoping. Set from server for sensitive cookies                                                 | ❌ Sent with every request (bandwidth cost); 4KB size limit; `document.cookie` API is painful to use raw; third-party cookies being phased out                                                                              | [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Set-Cookie)                                                                  |
| **IndexedDB**                 | Asynchronous NoSQL database in the browser. No size limit (beyond disk). Supports indexes, transactions, and structured data (not just strings)                    | `IndexedDB` API (raw), [Dexie.js](https://dexie.org/) (Promise-based wrapper)  | Use for large datasets (offline data, cached API responses, file blobs). Dexie simplifies schema migration, versioning, and querying                                                                      | ❌ Raw API is verbose and complex — always use Dexie or similar wrapper; no automatic sync with server; schema migrations require version bumps                                                                             | [MDN IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API), [Dexie.js](https://dexie.org/)                                         |
| **HTTP Caching**              | Browser and CDN caching controlled by response headers. Multi-level: memory cache → disk cache → service worker → CDN → origin                                     | Chrome DevTools Network tab (check `from cache`)                               | `Cache-Control` (controls who caches and how long), `ETag` + `If-None-Match` (conditional validation requests — `304 Not Modified`), `Last-Modified` + `If-Modified-Since`, `s-maxage` for CDN vs browser | ❌ Priority order: `Cache-Control` > `Expires` > heuristic. Stale CDN cache is the #1 "works in dev, broken in prod" bug. `no-cache` ≠ "don't cache" — it means "revalidate before using cache"                             | [MDN Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Cache-Control), [web.dev HTTP cache](https://web.dev/articles/http-cache) |
| **Service Worker**            | A JavaScript proxy that runs in a background thread, intercepts all network requests, and decides: serve from cache or go to network. Required for PWA and offline | Workbox (abstracts SW caching strategies), `sw.js` (custom)                    | Lifecycle: `install` (precache) → `activate` (clean old caches) → `fetch` (intercept). Strategies: Cache-first, Network-first, Stale-while-revalidate, Network-only, Cache-only                           | ❌ Requires HTTPS (except `localhost`); bugs in SW can hard-brick your app (bad cache = stuck forever); tricky to update (old SW serves old cache until all tabs close); test with DevTools → Application → Service Workers | [MDN Service Worker](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API), [Workbox docs](https://developer.chrome.com/docs/workbox)    |
| **API Caching (Client-side)** | Cache server responses in memory on the client to avoid redundant network requests. Different from HTTP caching — this is application-level                        | TanStack Query, SWR, Apollo Client                                             | `staleTime` (how long data is considered fresh), `cacheTime`/`gcTime` (how long to keep in memory), `refetchOnWindowFocus`, `invalidateQueries` on mutation, Apollo `fetch-policy`                        | ❌ Stale cache after mutation = UI shows old data; cache key collisions from non-unique query keys; memory leak if cache is never garbage-collected                                                                         | [TanStack Query caching](https://tanstack.com/query/latest/docs/framework/react/guides/caching)                                                         |
| **Data Normalization**        | Store entities flat (like a relational DB) — indexed by ID, no nesting. Prevents duplication and sync bugs across components                                       | Redux Toolkit `createEntityAdapter`, custom normalized store                   | `entities: { users: {1: {...}, 2: {...}}, posts: {...} }` + `ids: [1, 2]`. Reference by ID, not by embedding                                                                                              | ❌ Requires upfront schema design; denormalization needed at read time (selectors); unfamiliar to devs used to raw API response shapes                                                                                      | [Redux normalization guide](https://redux.js.org/usage/structuring-reducers/normalizing-state-shape)                                                    |

## Logging & Monitoring

| Topic                             | Core Concepts & Mental Model                                                                                                                 | Tools & Libraries                                                        | Key Techniques                                                                                                                                                             | Tradeoffs & Failure Modes                                                                                                                                                     | Resources                                                                         |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **Error Tracking**                | Capture unhandled JS errors in production with full stack trace, user context, and breadcrumbs — `console.error` is not enough               | Sentry *(most popular)*, Bugsnag, LogRocket, TrackJS                     | Global error handler (`window.onerror`, `unhandledrejection`), enrich with user ID/session, source maps for readable stack traces, ignore noise (browser extension errors) | ❌ Without source maps, stack traces point to minified code (`a.b.c` is useless). Too many events → quota exhaustion → sampling needed. PII in error context = compliance risk | [Sentry docs](https://docs.sentry.io/platforms/javascript/guides/react)           |
| **Real User Monitoring (RUM)**    | Measure actual user experience: Core Web Vitals, route timings, API latency — from real devices and connections, not synthetic labs          | `web-vitals` library, Datadog RUM, New Relic Browser, Sentry Performance | Instrument LCP/INP/CLS via `web-vitals`, send to analytics endpoint, segment by device/connection/geography                                                                | ❌ RUM data is noisy — outliers from slow devices/networks can skew averages; use p75/p95 percentiles not mean; PII in URLs must be scrubbed                                   | [web-vitals library](https://github.com/GoogleChrome/web-vitals)                  |
| **Product Analytics & Telemetry** | Track user behavior and business events (clicks, funnel steps, feature adoption). Answers "what are users actually doing?"                   | Amplitude, Segment, PostHog, Mixpanel                                    | Event batching (avoid per-click network requests), event taxonomy (`noun_verb` convention e.g. `cart_item_added`), avoid tracking PII, custom event properties             | ❌ Over-tracking = noise; under-tracking = blind spots; inconsistent event names across teams = unusable data. Tracking calls should never block the UI                        | [Segment tracking plan](https://segment.com/docs/getting-started/04-full-install) |
| **Session Replay**                | Record and replay real user sessions — mouse movement, clicks, DOM snapshots. Debug "how did this bug happen in production?"                 | LogRocket, FullStory, Hotjar, Microsoft Clarity (free)                   | Mask sensitive fields (passwords, card numbers), use for UX debugging + rage-click analysis, combine with error tracking for "replay session at error"                     | ❌ Privacy concerns — mask PII fields; performance overhead of recording DOM mutations; GDPR consent required in EU                                                            | [LogRocket docs](https://docs.logrocket.com/)                                     |
| **Alerting**                      | Proactive notification when error rates, performance metrics, or uptime cross a threshold. Reactive debugging is too slow for production     | Sentry Alerts, Datadog Alerts, PagerDuty, Opsgenie, UptimeRobot          | Error rate thresholds (not absolute counts — relative to traffic), anomaly detection, on-call rotation, alert fatigue avoidance (too many alerts = ignored)                | ❌ Threshold too sensitive = alert fatigue. Threshold too loose = missed incidents. % error rate is better than absolute count (a spike during low traffic vs. peak traffic)   | —                                                                                 |
| **Synthetic Monitoring**          | Scheduled automated tests that run against your production URL from multiple regions — catch outages before users do                         | Pingdom, Uptime Robot, Checkly, Vercel Analytics                         | Scheduled Lighthouse runs, multi-region uptime probes, critical user journey checks (can user log in? can they checkout?)                                                  | ❌ Doesn't reflect real user experience (no real network conditions/devices); can miss client-side JS errors that only appear with real user data                              | [Checkly docs](https://www.checklyhq.com/)                                        |
| **Custom Business Metrics**       | Instrument metrics that matter to the business, not just technical health: checkout conversion rate, feature adoption %, error recovery rate | Grafana + InfluxDB, Kibana (ELK), PostHog, Google Looker Studio          | Tag events with A/B test variant, funnel analysis, cohort analysis, dashboards for stakeholders                                                                            | ❌ Custom metrics need agreement between eng + product — what counts as a "conversion"? Inconsistent definitions across teams corrupt data                                     | —                                                                                 |

## Accessibility (a11y)

> **Reference:** [web.dev/learn/accessibility](https://web.dev/learn/accessibility)**Rule of thumb:** Use semantic HTML first. Add ARIA only when native semantics are insufficient — wrong ARIA is worse than no ARIA.
> 

| Topic                      | Core Concepts & Mental Model                                                                                                                                                            | Tools & Libraries                                                                              | Key Techniques                                                                                                                                                                                               | Tradeoffs & Failure Modes                                                                                                                                                                                                      | Resources                                                                                                    |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| **Keyboard Accessibility** | All interactive UI must be operable by keyboard alone. `Tab` (focus), `Enter`/`Space` (activate), `Arrow` keys (navigation within widget), `Escape` (dismiss)                           | `tabIndex`, `onKeyDown`, `focus-visible` CSS                                                   | Logical tab order, `tabIndex="0"` for custom interactive elements, `tabIndex="-1"` for programmatic focus, `focus-visible` for visible focus rings, keyboard shortcut hints                                  | ❌ `<div onClick>` is not keyboard accessible — use `<button>`. `tabIndex > 0` creates confusing tab order — avoid. Focus ring removal via `outline: none` without replacement = accessibility failure                          | [WCAG 2.1 – Keyboard](https://www.w3.org/WAI/WCAG21/Understanding/keyboard.html)                             |
| **Screen Reader Support**  | Screen readers announce what's on screen using the accessibility tree (built from HTML semantics). ARIA supplements the tree when native semantics are missing                          | NVDA (Windows), JAWS (Windows), VoiceOver (macOS/iOS), axe                                     | `aria-label` (names element), `aria-labelledby` (references visible text), `aria-describedby` (supplemental description), `role` (overrides implicit role), landmark regions (`<main>`, `<nav>`, `<header>`) | ❌ `aria-label` overrides visible text completely — inconsistency confuses users. Adding role without keyboard behavior = broken widget. Automated tools catch only ~30% of issues — manual VoiceOver/NVDA testing required     | [MDN ARIA](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA)                                  |
| **Focus Management**       | SPAs must manually manage focus on route changes, modal opens/closes, and dynamic content insertion. Native browser focus management is for multi-page apps                             | `focus-trap-react`, Headless UI, Radix UI, `useRef().focus()`                                  | Move focus to modal on open, return focus to trigger on close, focus trap inside modal (Tab cycles within), skip-nav link for bypassing repeated navigation                                                  | ❌ No focus management in modal = screen reader user can't reach modal content. No focus restoration on close = user loses their place                                                                                          | [WCAG – Focus Order](https://www.w3.org/WAI/WCAG21/Understanding/focus-order.html)                           |
| **Color & Contrast**       | WCAG requires minimum contrast ratios: 4.5:1 for normal text, 3:1 for large text (18px+ bold or 24px+). Contrast affects users with low vision and situational impairments (bright sun) | axe DevTools, Lighthouse, [Colour Contrast Checker](https://colourcontrast.cc/), Figma plugins | Use real contrast checking tools — never eyeball. Design accessible color palette from the start, not as afterthought. Provide `prefers-color-scheme` dark mode                                              | ❌ Placeholder text is usually too light — style it separately. Focus indicators need 3:1 contrast against adjacent colors. Color alone cannot convey information (colorblind users)                                            | [WCAG Contrast](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html)                           |
| **Forms Accessibility**    | Labels must be programmatically associated with inputs. Error messages must be announced to screen readers. Required fields must be indicated beyond just color                         | React Hook Form + Zod, `aria-describedby`, `aria-invalid`, `aria-required`                     | `<label htmlFor="id">` ↔ `<input id="id">`, `aria-describedby="error-id"` links error to input, `aria-invalid="true"` when field has error, `role="alert"` on error message for live announcement            | ❌ Placeholder as label = fails when user types (label disappears). `aria-placeholder` is not a substitute for `<label>`. Error message not linked with `aria-describedby` = screen reader user doesn't know which field failed | [WebAIM Forms](https://webaim.org/techniques/forms)                                                          |
| **Alt Text & Media**       | Images need text alternatives. Purpose drives the description — not literal visual description. Decorative images get `alt=""` (not missing `alt`)                                      | Standard `alt` attribute                                                                       | Functional image (button icon): describe action ("Search"). Informational image: describe content. Complex image (chart): use `aria-describedby` with full description nearby. Decorative: `alt=""`          | ❌ Missing `alt` = screen reader reads filename. `alt="image"` or `alt="photo of"` = useless. SVG inline: add `role="img"` + `<title>` + `aria-labelledby`                                                                      | [WebAIM Alt Text](https://webaim.org/techniques/alttext)                                                     |
| **Animation & Motion**     | Animations can trigger vestibular disorders (dizziness, nausea). `prefers-reduced-motion` media query lets users opt out of motion                                                      | CSS `@media (prefers-reduced-motion: reduce)`, Framer Motion `useReducedMotion()`              | Disable or simplify animations when `prefers-reduced-motion: reduce` is set, provide pause controls for auto-playing content, avoid rapid flashing (seizure risk: 3+ flashes/sec)                            | ❌ Ignoring `prefers-reduced-motion` is an accessibility failure and WCAG violation (Level A). Auto-playing video with motion on landing page = inaccessible                                                                    | [MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion) |
| **Auditing**               | Automated tools + manual testing. Automated: fast, consistent, catches ~30% of issues. Manual: required for real confidence                                                             | axe DevTools, `jest-axe`, Lighthouse, NVDA/VoiceOver, keyboard-only walkthrough                | `jest-axe` in component tests (`expect(await axe(container)).toHaveNoViolations()`), Lighthouse a11y score, manual keyboard navigation walkthrough per feature, screen reader test on critical flows         | ❌ 100% Lighthouse score ≠ accessible app — many failures require human judgment. Automated tools miss: focus order, meaningful alt text quality, logical reading order                                                         | [jest-axe](https://github.com/nickcolley/jest-axe)                                                           |

## Low-Level Design — UI Patterns

> **Mental Model:** Each pattern is a solution to a recurring problem. Know: what problem it solves, what the edge cases are, and how to make it accessible and performant.
> 

| Pattern                       | Problem It Solves                                                                                               | Key Implementation Details                                                                                                                                                                                   | Edge Cases & Failure Modes                                                                                                                                                                                                                                             | Real-world Examples                                                                  |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **Infinite Scroll**           | Loading large datasets without pagination UI. Feels native/app-like                                             | `IntersectionObserver` on a sentinel element at list bottom, TanStack Query `useInfiniteQuery`, combine with virtualization for large lists                                                                  | ❌ No way to jump to a position (bookmarking, back navigation breaks); "scroll restoration" on back navigation is hard; must handle loading/error state at bottom; combine with `react-window` for DOM performance                                                      | Twitter/Instagram feed, YouTube recommendations                                      |
| **Virtualized List**          | Rendering 1000+ items in DOM freezes the browser. Only visible items should exist in DOM                        | `react-window` (`FixedSizeList`/`VariableSizeList`), TanStack Virtual, `react-virtuoso` (dynamic heights)                                                                                                    | ❌ Dynamic/unknown row heights require measuring (use `VariableSizeList`); accessibility: screen readers can't access offscreen rows; `Ctrl+F` in-page search won't find hidden rows                                                                                    | Chat history, data tables, autocomplete results, contact lists                       |
| **Autocomplete / Search**     | Live suggestions as user types — minimize API calls while maintaining responsiveness                            | Debounce input (150-300ms), `AbortController` to cancel stale requests, Fuse.js for client-side fuzzy search, `aria-autocomplete`, `role="combobox"`, `aria-activedescendant`                                | ❌ Race condition: fast typing → slow request from earlier keystroke arrives last → wrong suggestions shown (fix: abort stale requests); no minimum character count = too many requests; keyboard navigation (`ArrowUp`/`ArrowDown`/`Enter`/`Escape`) required for a11y | Google search, GitHub file finder, address autocomplete                              |
| **Pagination**                | Navigate large datasets in discrete chunks with persistent URL state                                            | Offset: `?page=2&limit=20` (simple, supports page jump). Cursor: `?cursor=<id>` (consistent for live data). Store in URL (`useSearchParams`) for shareability                                                | ❌ Offset pagination is inconsistent with live data (new items shift pages); cursor pagination can't jump to arbitrary page; deep offset queries are slow on large DB tables (use cursor for >10k rows)                                                                 | Search results (offset), activity feed (cursor)                                      |
| **Accordion**                 | Progressive disclosure — show/hide sections to reduce visual noise                                              | `<details>`/`<summary>` (native, accessible for free) or custom with `aria-expanded`, `aria-controls`, `id` pairing; single vs multi-expand mode                                                             | ❌ Using `display: none` vs `visibility: hidden` vs `height: 0` affects animation and accessibility (hidden content reachable by Tab?); `aria-expanded` must update on toggle; animated height needs `grid-row` trick (not `max-height` hack)                           | FAQ pages, settings panels, sidebar navigation                                       |
| **Nested Comments**           | Threaded comment trees with recursive structure and reply/collapse functionality                                | Recursive component (`Comment` renders `Comment[]`), flatten tree with depth metadata for virtualization, cursor pagination per thread                                                                       | ❌ Deep recursion = stack overflow for very deep trees (flatten server-side with depth field); loading all replies at once = slow (lazy-load on "Show replies"); collapse state management per node                                                                     | Reddit, YouTube, GitHub PR comments                                                  |
| **Optimistic UI**             | Instant feedback before server confirms — makes mutations feel instant                                          | TanStack Query `onMutate` (snapshot + optimistic update) + `onError` (rollback) + `onSettled` (sync), or Zustand optimistic state                                                                            | ❌ Rollback UX is jarring if not handled gently (toast: "Failed to save"); don't use for destructive/financial operations; race conditions on rapid mutations (e.g. like/unlike spam)                                                                                   | Like buttons, follow/unfollow, cart add/remove, drag-and-drop reorder                |
| **Shimmer / Skeleton UI**     | Perceived performance — users tolerate loading better when they see layout structure vs blank screen or spinner | CSS animation (`background: linear-gradient` + `keyframes`), Tailwind `animate-pulse`, match skeleton shape to real content layout                                                                           | ❌ Skeleton that doesn't match content layout causes CLS on load; too many skeletons on one page = busy/noisy; prefer streaming + Suspense for granular loading states in Next.js                                                                                       | Facebook card skeletons, LinkedIn feed, YouTube thumbnail loading                    |
| **Image Slider / Carousel**   | Display multiple images/items in a constrained space with navigation                                            | Swiper.js, Embla Carousel, Keen Slider; implement: `overflow: hidden` parent, translate on index change, touch/pointer events for swipe; `role="region"` + `aria-label`, prev/next buttons with `aria-label` | ❌ Auto-play carousels are an accessibility violation (moving content without user control — add pause button); keyboard navigation required; lazy-load off-screen slides; avoid infinite loop jank on last→first transition                                            | Product image galleries, testimonials, hero banners                                  |
| **Backend-Driven UI (BDUI)**  | Server sends UI configuration (JSON) and client renders it dynamically. UI changes without app deploy           | JSON schema describing components + props, `react-jsonschema-form`, headless CMS, custom renderer                                                                                                            | ❌ Hard to maintain type safety (JSON is untyped); complex conditional rendering logic becomes unreadable JSON; limited to predefined component palette; debugging is harder (can't trace to source code line)                                                          | A/B test variants, CMS-managed pages, form builders, feature-flag controlled layouts |
| **Realtime Collaborative UI** | Multiple users editing the same document simultaneously with conflict resolution                                | Operational Transforms (OT) or CRDTs (`yjs`, `automerge`), WebSocket for transport, presence indicators                                                                                                      | ❌ Last-write-wins = data loss in concurrent edits; CRDTs solve conflicts but add payload overhead; showing presence (who's viewing/editing) requires server-side state per session                                                                                     | Google Docs, Figma, Notion, code collaboration (VS Code Live Share)                  |
| **YouTube-style Chat**        | High-volume live chat with message streaming, moderation, and visual rendering at scale                         | WebSocket or SSE for delivery, client-side virtualization (`react-window`) for rendering, rate-limiting on message send, profanity filter + moderation queue                                                 | ❌ Rendering 1000 messages/min without virtualization = DOM collapse; no deduplication = duplicate messages on reconnect; no rate limiting = chat flood attack; mobile: soft keyboard pushes chat view up (CSS `env(keyboard-insets)`)                                  | YouTube Live, Twitch chat, Discord                                                   |
