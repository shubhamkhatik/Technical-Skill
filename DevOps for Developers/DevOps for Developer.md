# DevOps for Developer

# DevOps for Developers — 01. Linux & Terminal

> **Mental Model:** As a developer you don't need to be a Linux sysadmin. You need to be comfortable enough to: SSH into a server, read logs, debug a running process, manage files, and not accidentally break things. Every cloud server, Docker container, and CI runner is Linux.
> 

| Skill | Core Concepts & Mental Model | Key Commands & Techniques | Tradeoffs & Failure Modes | Resources |
| --- | --- | --- | --- | --- |
| File System Navigation | Linux file tree: everything is a file. / is root. Key dirs: /etc (system configs), /var/log (logs), /home (user dirs), /tmp (cleared on reboot), /usr/bin (installed binaries), /proc (live kernel/process info) | ls -la, cd, pwd, find / -name "file" -type f, tree, du -sh * (disk usage per dir), df -h (disk free), stat file (metadata) | rm -rf with wrong path = unrecoverable data loss. Always double-check path before destructive commands. /proc/meminfo and /proc/cpuinfo are useful for inspecting running system without installing tools | [Linux Command Line (free book)](https://linuxcommand.org/tlcl.php) |
| File Operations & Permissions | Linux permissions: owner / group / others × read(4) / write(2) / execute(1). Octal notation: 755 = rwxr-xr-x. Symbolic: chmod +x file | cp, mv, rm -rf, mkdir -p (create nested dirs), touch, cat, less, head -n 20, tail -f (live log follow), grep -r "text" ., chmod 755 file, chown user:group file, ln -s target link (symlink) | Never run chmod 777 — world-writable files are a security risk. chown -R as root on wrong directory can break system binaries. tail -f is the most-used command for watching live logs in production | [chmod Calculator](https://chmod-calculator.com/) |
| Process Management | Every running program is a process with a PID. Parent-child relationships. Signals: SIGTERM (15) = graceful shutdown request, SIGKILL (9) = force kill (no cleanup), SIGHUP (1) = reload config | ps aux (all processes), top / htop (live — htop is better), kill -15 PID (graceful), kill -9 PID (force), pkill node (by name), lsof -i :3000 (what's using port 3000), nohup command & (survive logout), jobs / fg / bg | kill -9 skips cleanup handlers — use kill -15 first, wait 5s, then kill -9 if needed. Zombie processes = child exited but parent never collected exit status (ps shows Z state). lsof -i :3000 is the most useful command when "port already in use" | [DigitalOcean Process Guide](https://www.digitalocean.com/community/tutorials/process-management-in-linux) |
| Text Processing | Parse logs, extract data, transform output — the most frequent real-world Linux task. Pipe chains process data as streams — no memory issue for huge files | grep -E "ERROR | WARN" app.log (regex), grep -v "health" (exclude), awk '{print $1}' (print column), sed 's/old/new/g' (replace), sort | uniq -c | sort -rn (count + rank occurrences), wc -l (line count), cut -d',' -f1 (CSV column), jq '.users[].name' (JSON parsing — modern essential) | jq is not installed by default — apt install jq. awk and sed have subtly different regex syntax. Avoid parsing logs with regex in application code — ship structured JSON logs and use jq or a log aggregator |
| Environment & Shell | Shell (bash/zsh) interprets commands. Environment variables are key=value pairs inherited by child processes. PATH controls where shell searches for binaries | export VAR=value (current session), echo $VAR, env (all vars), printenv VAR, which node (binary location), type command (alias vs binary), source ~/.zshrc (reload config). Add to ~/.zshrc or ~/.bashrc for persistence | export in terminal = session only. Secrets in .bashrc/.zshrc = visible in plain text and potentially git-tracked. Use direnv (per-directory .envrc files) for project-specific env vars without polluting global shell | [direnv](https://direnv.net/) |
| SSH | Encrypted remote terminal access. Key-based auth: your private key + server's authorized_keys. More secure and more convenient than passwords. Never enable password auth on production servers | ssh-keygen -t ed25519 -C "email" (generate keypair), ssh-copy-id user@ip (add pubkey to server), ssh user@ip, ssh -i key.pem user@ip (AWS style), chmod 400 key.pem (required by SSH), ~/.ssh/config for saved host aliases, ssh -L 5432:localhost:5432 user@server (port forwarding — access remote DB locally) | Private key must never leave your machine. PEM files require chmod 400 — SSH refuses overly-permissive keys. ed25519 is preferred over RSA (shorter key, same security). SSH port forwarding is the safest way to access remote DBs locally without exposing DB port publicly | [SSH Essentials](https://www.digitalocean.com/community/tutorials/ssh-essentials-working-with-ssh-servers-clients-and-keys) |
| Cron Jobs | Schedule recurring tasks. Runs as the crontab owner's user. Format: minute hour day month weekday command (5 fields) | crontab -e (edit), crontab -l (list), 0 2 * * * /scripts/backup.sh (daily at 2am), */5 * * * * (every 5 min). Always redirect output: >> /var/log/cron.log 2>&1. Use absolute paths for binaries: /usr/bin/node not node | Cron uses minimal PATH — relative binary names silently fail. Silent failures are the #1 cron bug — always log output. Test scripts manually before adding to crontab. For distributed systems use BullMQ repeatable jobs or Inngest instead of cron — avoids multi-instance double-execution | [Crontab Guru](https://crontab.guru/) |
| Networking Commands | Debug connectivity issues, inspect open ports, trace network paths | curl -I https://api.example.com (HTTP headers), curl -v (verbose — full request/response), wget, ping, traceroute / tracepath, netstat -tulpn (open ports + listening processes), ss -tulpn (modern replacement for netstat), nc -zv host port (test port connectivity), dig domain (DNS lookup), nslookup domain | curl -v is the most useful tool for debugging API calls from a server. ss -tulpn shows exactly what's listening on which port. If curl works but browser doesn't = DNS or CORS issue, not a server issue | — |
| System Monitoring | Understand resource usage before scaling or debugging performance issues | htop (interactive process + CPU/memory), free -h (memory), df -h (disk), iostat (disk I/O), vmstat (CPU/memory/IO overview), uptime (load averages), dmesg (kernel messages — hardware/boot issues), journalctl -u myservice -f (systemd service logs, live) | Load average > number of CPU cores = CPU bottleneck. Memory usage near 100% + swap increasing = memory leak. Disk full = silent failures (logs stop writing, DB crashes). Check df -h before diagnosing mysterious errors | — |
| Package Management | Install, update, remove system packages. apt (Debian/Ubuntu), yum/dnf (RHEL/Amazon Linux) | apt update (refresh package index), apt install -y package, apt remove package, apt list --installed, which binary (confirm install). On Alpine (Docker): apk add --no-cache package | Always apt update before apt install in Docker or CI — stale package index = version not found errors. Use apt-get (non-interactive) in Dockerfiles, not apt (interactive). Pin package versions in Dockerfiles for reproducible builds | — |

# DevOps for Developers — 02. Git & Version Control

> **Mental Model:** Git tracks snapshots of your project, not diffs. Three areas: Working Directory (files you edit) → Staging Area (what you mark for commit) → Repository (committed history). Commits are immutable content-addressed objects — you never modify history, you add new commits on top.

# DevOps for Developers — 03. CI/CD Pipelines

> **Mental Model:** CI/CD makes deployment a non-event — small, frequent, automated, and reversible. CI (Continuous Integration) catches bugs early by building and testing every commit. CD (Continuous Delivery/Deployment) removes manual steps from shipping code. The goal: confidence to deploy 10 times a day without fear.

# DevOps for Developers — 04. Docker & Containerization

> **Mental Model:** A container is an isolated process on the host OS kernel — not a VM. It packages the app + its exact runtime dependencies into a portable unit that runs identically everywhere. Image = immutable blueprint. Container = running instance. Docker solved "works on my machine." Containers are now the universal unit of deployment.
>

# DevOps for Developers — 05. Cloud — AWS for Developers

> **Mental Model:** As a developer you don't need to know every AWS service (there are 200+). You need to know: how to deploy an app, store files, manage a database, handle secrets, send traffic to the right place, and know when things break. AWS is the default cloud — these services appear in almost every production stack.

## Infrastructure as Code (IaC)

> **Mental Model:** Infrastructure as Code means your servers, databases, networking, and cloud resources are defined in version-controlled files — not clicked through a GUI. Benefits: reproducible environments, code review for infra changes, disaster recovery by re-applying code, and no "snowflake servers" that only one person knows how to configure.

| Terraform Basics                 | Declarative IaC tool. You describe the desired end state — Terraform figures out how to get there. Provider plugins talk to AWS/GCP/Azure APIs. State file tracks what Terraform has created            | terraform init (download providers), terraform plan (preview changes — always review before apply), terraform apply (create/update resources), terraform destroy (teardown). main.tf: provider, resource blocks. variables.tf: input variables. outputs.tf: values to expose | terraform apply without review = accidental deletion of production resources. State file contains sensitive data — store in S3 + DynamoDB locking (never commit to git). Drift: someone manually changes a resource → state out of sync → next apply may delete the manual change | [Terraform docs](https://developer.hashicorp.com/terraform/docs) |
| Terraform State                  | State file (terraform.tfstate) is Terraform's source of truth — maps config to real resources. Remote state: store in S3 (shared across team, locked with DynamoDB to prevent concurrent applies)       | backend "s3": bucket, key, region, dynamodb_table. terraform state list (show all resources in state). terraform state show aws_instance.web (inspect a resource). terraform import (bring existing resource under Terraform management)                                     | Local state = only works on one machine. No state locking = two applies simultaneously = corrupted state. Never manually edit tfstate. Losing state file = Terraform can no longer manage existing resources (use terraform import to recover)                                    | —                                                                |
| Terraform Modules                | Reusable, parameterized infrastructure components. Avoid copy-pasting the same EC2/RDS/VPC config across environments                                                                                   | module "web_server" { source = "./modules/ec2", instance_type = var.instance_type }. Variables: input parameters. Outputs: values exposed to calling module. Public registry: registry.terraform.io (AWS VPC module, EKS module)                                             | Module versioning: pin module source to a specific version tag. Over-modularizing small infra = unnecessary abstraction. Modules hide complexity — understand what a module creates before using it in production                                                                 | [Terraform Registry](https://registry.terraform.io/)             |
| AWS CDK (Developer-friendly IaC) | Define AWS infrastructure in TypeScript/Python/Java — not HCL or YAML. Compiles to CloudFormation. Best for developers who prefer typed languages over declarative config                               | npm install aws-cdk-lib. Stack class defines resources. new ec2.Vpc(this, 'VPC'), new ecs.FargateService(this, 'Service'). cdk synth (generate CloudFormation template), cdk deploy (deploy stack), cdk diff (preview changes)                                               | CDK generates CloudFormation under the hood — still has CFN limitations (deploy rollback complexity). Abstraction can hide what's actually being created — run cdk synth and review the generated template. CDK versioning: breaking changes between major versions               | [AWS CDK docs](https://docs.aws.amazon.com/cdk)                  |
| Docker Compose as Local IaC      | For local development, docker-compose.yml is your infrastructure-as-code — defines your full local environment reproducibly                                                                             | version: '3.9'. services: app (build: ., ports, env_file, depends_on, healthcheck), postgres (image: postgres:16, volumes, environment), redis (image: redis:7-alpine). docker compose up -d, docker compose down                                                            | Treat docker-compose.yml as code — commit it, review changes. Use .env file for local secrets (not hardcoded in compose file). depends_on + healthcheck: condition: service_healthy ensures app waits for DB to be ready                                                          | —                                                                |
| Pulumi (2026 Alternative)        | IaC using real programming languages (TypeScript, Python, Go) — not a DSL like HCL. State managed by Pulumi Cloud or self-hosted. Growing adoption in 2026                                              | const vpc = new aws.ec2.Vpc("vpc", { cidrBlock: "10.0.0.0/16" }). pulumi up (preview + apply), pulumi destroy. Full TypeScript: loops, conditionals, functions, types — more expressive than Terraform HCL                                                                   | Pulumi is less mature than Terraform — smaller community, fewer examples. But TypeScript developers find it more natural than learning HCL. Use Terraform if team already knows it — switching has a cost                                                                         | [Pulumi docs](https://www.pulumi.com/docs)                       |
| GitOps                           | Infrastructure and application config in git. Any change to infra goes through a PR → reviewed → merged → automatically applied. ArgoCD (K8s) and Terraform Cloud/Atlantis (Terraform) implement GitOps | ArgoCD: watches a git repo, syncs K8s cluster to match manifests. Atlantis: runs terraform plan on PR, terraform apply on merge. Branch = environment: merge to main → deploy to production. Feature branches → preview environments                                         | GitOps requires discipline — manual kubectl apply or terraform apply outside git = drift. ArgoCD auto-sync can be dangerous if misconfigured (any bad commit auto-deploys). Use manual sync + approval for production in early adoption                                           | [ArgoCD docs](https://argo-cd.readthedocs.io/)                   |
